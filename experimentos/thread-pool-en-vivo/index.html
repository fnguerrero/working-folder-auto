Las cuentas de servilleta

Qué es el thread pool y por qué tu API depende de él

En ASP.NET Core cada pedido HTTP termina siendo un work item del ThreadPool: Kestrel lo recibe en sus hilos de I/O y lo encola, y un hilo del pool lo toma, corre tu middleware, tu controller y tu código. Lo mismo pasa con cada continuación después de un await, con cada callback de Task.Run, con los timers y con los consumidores de colas. Si el pool no tiene un hilo libre, el pedido espera en esa cola antes de empezar a ejecutarse: no está en ningún log tuyo, no está en la base, está esperando un hilo.

El pool arranca con pocos hilos: el mínimo es Environment.ProcessorCount (4 en una máquina de 4 núcleos, 2 en un pod con 2 vCPU). Hasta ese mínimo crea hilos sin pensarlo apenas hay trabajo. De ahí para arriba se pone conservador, y con razón: para código que usa CPU, más hilos que núcleos es puro cambio de contexto. Dos mecanismos deciden si agregar más:

  • Hill climbing: un controlador que mueve la cantidad de hilos de a poco y mide si el throughput (work items completados por segundo) mejora. Necesita señal: si nada termina, no aprende nada.
  • El gate thread: un hilo de vigilancia que se despierta cada 500 ms. Si ve que hay trabajo encolado y todos los hilos están ocupados sin que se haya completado nada hace rato, fuerza un hilo más. Uno. Cada medio segundo.

Ahí está el problema: si tus pedidos tienen el hilo tomado pero sin hacer nada (esperando a la base con .Result, o con una consulta sincrónica), el pool solo puede crecer a razón de dos hilos por segundo. Si necesitás 21 hilos a la vez y arrancaste con 4, son más de 8 segundos durante los cuales la cola crece sin frenar. Eso es la inanición del thread pool (thread pool starvation): la API no está caída, la CPU está casi en cero, la base está tranquila, y los pedidos tardan segundos o dan timeout.

Las tres formas de esperar la I/O

Bloqueando el hilo (así se cuelga)

// .Result / .Wait() / GetAwaiter().GetResult()
var cliente = _db.Clientes
    .FirstOrDefaultAsync(c => c.Id == id).Result;

// I/O sincrónica: el hilo queda esperando igual
var cliente = _db.Clientes.FirstOrDefault(c => c.Id == id);
var json = _http.GetStringAsync(url).GetAwaiter().GetResult();
Thread.Sleep(100);
lock (_cache) { /* algo lento acá adentro */ }

// La peor: parece async pero bloquea
return Task.Run(() => Procesar()).Result;

Soltando el hilo (async de punta a punta)

public async Task<ActionResult<Cliente>> Get(int id)
{
    var cliente = await _db.Clientes
        .FirstOrDefaultAsync(c => c.Id == id);
    var extra = await _http.GetStringAsync(url);
    await Task.Delay(100);
    await _semaforo.WaitAsync();
    return cliente is null ? NotFound() : cliente;
}

// Mientras la base trabaja, el hilo volvió al pool
// y atiende otros pedidos. Cuando la respuesta llega,
// la continuación se encola como un work item nuevo.

En el simulador, await es «el hilo se libera durante la I/O y la continuación vuelve a la cola»; .Result es «el hilo queda bloqueado en Task.Wait, y el pool lo sabe si es .NET 6 o más nuevo»; I/O sincrónica es «el hilo queda bloqueado y el pool no tiene idea» (una consulta sin Async, un lock, un Thread.Sleep, un ManualResetEvent, un socket sincrónico).

Qué cambió en .NET 6

Desde .NET 6 el pool está escrito en C# (el PortableThreadPool) y tiene un mecanismo nuevo: cuando un hilo del pool entra a Task.Wait (y por lo tanto a .Result y a GetAwaiter().GetResult()) sobre una tarea que todavía no terminó, le avisa al pool. El pool sube su meta de hilos a «mínimo + hilos bloqueados» y crea los que faltan casi sin demora: los primeros 1,25 × núcleos de inmediato, y el resto de a 0,25 × núcleos con pausas que crecen de 25 a 250 ms. Por eso el escenario «Lo mismo en .NET 8» se recupera en un segundo y medio en vez de 17.

No es una solución, es un airbag. Sirve solo para Task.Wait: un lock, una consulta sincrónica de ADO.NET, un HttpWebRequest viejo o un Thread.Sleep no avisan a nadie, y ahí .NET 8 se comporta como .NET Core 3.1 (probá «I/O sincrónica en .NET 8»). Y el precio son hilos: 40 hilos para hacer el trabajo que 4 hacen con await, cada uno con su stack (1 MB reservado por defecto) y su cambio de contexto. Con una base más lenta o más tráfico, la cantidad de hilos crece hasta donde haga falta, y en un pod con poca memoria eso también duele.

Cómo saber si te está pasando en producción

  • La forma de la latencia. No es una subida proporcional al tráfico: es una rampa que crece durante segundos y después baja de golpe cuando el pool «alcanzó». CPU baja, base tranquila, timeouts del lado del cliente. Después de un deploy o un pico, no en régimen.
  • Contadores. dotnet-counters monitor --process-id <pid> System.Runtime y mirá threadpool-thread-count (sube de a uno cada 500 ms) y threadpool-queue-length (debería ser casi siempre 0). Desde código, ThreadPool.ThreadCount y ThreadPool.PendingWorkItemCount se pueden exponer como métricas; en .NET 9 también están en System.Runtime por Meter para OpenTelemetry.
  • Stacks. dotnet-stack report --process-id <pid> o un dump con dotnet-dump y clrstack -all: si ves 30 hilos del pool parados en Monitor.Wait, Task.Wait, ManualResetEventSlim.Wait o en un SqlCommand.ExecuteReader sin Async, ya está.
  • Eventos. El runtime emite ThreadPoolWorkerThreadAdjustment (razón: Starvation) y los eventos de ThreadPoolWorkerThreadStart; se ven con dotnet-trace o PerfView. Hay una guía oficial paso a paso, está en las fuentes.

Qué hacer

  • Async de punta a punta. Es la única solución de verdad. Cada .Result, .Wait() y GetAwaiter().GetResult() en el camino de un pedido es una bomba de tiempo; cada método sincrónico de I/O (ToList() en vez de ToListAsync(), ExecuteReader en vez de ExecuteReaderAsync, File.ReadAllText) también. Un analizador ayuda: Microsoft.VisualStudio.Threading.Analyzers (VSTHRD002) marca los bloqueos.
  • Si hoy no podés cambiar el código, ThreadPool.SetMinThreads(n, n) al arrancar (o "System.Threading.ThreadPool.MinThreads": n en runtimeconfig.json) con un n bastante más alto que los hilos que necesitás en pico. Compra tiempo. No arregla, y hace que la próxima vez explote con más tráfico y menos aviso.
  • Limitá la concurrencia hacia lo que es lento con SemaphoreSlim.WaitAsync o con el pool de conexiones: si la base soporta 50 consultas a la vez, 300 pedidos simultáneos no la van a apurar, y con async la espera al menos no gasta hilos.
  • No disfraces lo sincrónico. Task.Run(() => algoSincrónico()).Result bloquea dos hilos en vez de uno. async void no existe para esto.
  • ASP.NET Framework (el viejo) tiene un problema peor: .Result en un controller con SynchronizationContext es un deadlock directo, no una lentitud. Ahí ConfigureAwait(false) en las librerías evita el deadlock, pero no evita el hilo bloqueado. En ASP.NET Core no hay SynchronizationContext y ConfigureAwait(false) no cambia nada de esto.

Qué es y qué no es este modelo

Es una simulación con un reloj de 1 ms que reproduce las reglas documentadas del pool: hilos mínimos iguales a los núcleos (creados sin demora), un gate thread que cada 500 ms agrega un hilo si hay cola y todos están ocupados, hilos de más que se retiran después de 20 s sin trabajo, CPU repartida entre los hilos que la quieren (si hay más hilos corriendo que núcleos, cada uno avanza más lento) y, en .NET 6+, la inyección por bloqueo con las constantes de PortableThreadPool.Blocking.cs (1,25 y 0,25 × núcleos, pasos de 25 ms con tope de 250 ms). Las llegadas son Poisson y la I/O varía ±20 %.

No modela el hill climbing (que en la práctica suma algún hilo más cuando hay progreso parcial, y también los saca), ni la presión de memoria que frena la inyección por bloqueo, ni el ajuste del gate thread por uso de CPU, ni el costo real de los cambios de contexto, ni las colas locales por hilo, ni la variación del tiempo de CPU. Los números son del modelo; las formas de las curvas y los órdenes de magnitud son los que vas a ver en un servidor real. Si querés el dato duro de tu runtime, el mismo escenario se reproduce en diez líneas: un endpoint con Thread.Sleep(100) o .Result, 200 pedidos/s con bombardier o k6, y dotnet-counters al lado.
