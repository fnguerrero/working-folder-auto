Comparación final

Qué se mide

  • Páginas hoja y tamaño. Cuántas páginas de 8 KB ocupa el nivel que tiene las filas (en SQL Server, con índice agrupado, eso es la tabla). Más páginas es más disco, más lecturas y más memoria para lo mismo.
  • Llenado. Promedio de qué tan llena quedó cada hoja. Con claves secuenciales las páginas se llenan completas; con claves al azar el B-tree se estabiliza en ln 2 ≈ 69 %, que es un resultado clásico (Yao, 1978).
  • Divisiones de página. Cada vez que una hoja se llena hay que partirla, mover filas y escribir dos páginas (y a veces el padre). Son las escrituras más caras del índice y las que llenan el log de transacciones.
  • Fragmentación. Porcentaje de hojas cuya siguiente en orden lógico no está físicamente a continuación. Es la avg_fragmentation_in_percent de sys.dm_db_index_physical_stats, aproximada. Castiga los barridos de rango en disco, no tanto las búsquedas puntuales.
  • Páginas calientes. Cuántas hojas distintas se escribieron en las últimas 1.000 inserciones. Con claves secuenciales son un puñado y viven en caché; con claves al azar son casi todas, así que cada inserción es, potencialmente, una lectura de disco y una página sucia más.

Qué suele salir

  • GUID aleatorio (NEWID(), Guid.NewGuid()): llenado ≈ 69 %, fragmentación ≈ 100 %, prácticamente todas las páginas calientes. Ocupa más por la clave de 16 bytes y por el 31 % de aire en cada página. En SQL Server, además, la clave agrupada viaja dentro de cada índice no agrupado, así que los 16 bytes se pagan una vez por índice.
  • int identity: llenado ≈ 100 %, sin fragmentación, 15 páginas calientes. Es el mejor caso, y su costo escondido es otro: todas las inserciones pelean por la misma última página (PAGELATCH_EX), algo que SQL Server 2019 mitiga con OPTIMIZE_FOR_SEQUENTIAL_KEY.
  • GUID secuencial estricto (NEWSEQUENTIALID(), el SequentialGuidValueGenerator de EF Core): igual que identity, con páginas más grandes por la clave de 16 bytes.
  • GUID v7 (Guid.CreateVersion7(), .NET 9): es el más interesante. Lleva el tiempo en milisegundos adelante, así que las inserciones van siempre al final del índice: las páginas calientes son pocas, como con identity, y eso ya es la mayor parte del beneficio. Pero dentro del mismo milisegundo sus bits son aleatorios, así que con varias inserciones por milisegundo las claves de ese ms caen desordenadas sobre la última página. En el modelo de SQL Server eso rompe la optimización de "página nueva con la fila nueva" y provoca divisiones a la mitad: el llenado baja a 55-70 % y aparece fragmentación. En PostgreSQL, que deja la página izquierda al 90 % en cualquier división del extremo derecho, el efecto es mucho menor. Probá con 1, 5 y 50 inserciones por milisegundo.

Qué hacer con esto

  • Si la clave la pone la base, int o bigint identity siguen siendo la opción más barata para el índice agrupado. Se puede tener además un GUID como clave alternativa (índice único no agrupado) para exponerlo afuera.
  • Si la clave la genera la aplicación (para armar grafos de objetos antes de guardar, para sistemas distribuidos), usá un GUID con orden temporal: Guid.CreateVersion7() en .NET 9, o el generador secuencial de EF Core para SQL Server. Nunca Guid.NewGuid() como clave agrupada en tablas que crecen.
  • Cuidado con el orden de SQL Server: compara los GUID por grupos de bytes de derecha a izquierda (los últimos 6 bytes primero). Un v7 "de RFC" no es secuencial para SQL Server si se guarda como uniqueidentifier; EF Core lo sabe y por eso su generador acomoda los bytes. En PostgreSQL y en el orden de .NET, el v7 sí es secuencial tal cual.
  • En PostgreSQL la tabla es un heap y el orden físico no lo decide la clave: lo que sufre es el índice de la primaria, con los mismos efectos de esta simulación. PostgreSQL 18 trae uuidv7() nativo; antes, gen_random_uuid() es v4.
  • Si ya tenés una tabla con GUID aleatorios, un fillfactor menor y un rebuild periódico reducen las divisiones, a costa de más páginas. No lo arregla: lo administra.

Cómo está hecho el modelo (y qué no es)

  • Páginas de 8.192 bytes con 96 de cabecera y 10 de sobrecarga por fila. La capacidad de una hoja sale de ahí: con 100 bytes de carga entran 71 filas con clave int y 64 con GUID.
  • Las hojas se encadenan en orden lógico y cada página nueva recibe el siguiente número físico, como una asignación secuencial en el archivo. Las páginas internas se numeran en la misma secuencia, por eso hasta el caso perfecto muestra una fragmentación residual chica.
  • Divisiones: siempre 50/50, salvo cuando se llena la última hoja y la fila nueva es la mayor de todas. Ahí SQL Server abre una página nueva solo con la fila nueva, PostgreSQL deja la vieja al 90 % (su fillfactor por defecto) y el B-tree "de libro" parte a la mitad igual.
  • No hay borrados, ni actualizaciones, ni reutilización de espacio, ni fillfactor configurable, ni concurrencia (no se modela la contención de la última página), ni caché con tamaño. Los GUID aleatorios salen de un generador determinista para que la misma semilla repita el resultado. Es un modelo para entender el mecanismo, no un benchmark del motor.
