    PostgreSQL para los que vienen de SQL Server

    Una guía práctica, para alguien que lleva años con T-SQL y SSMS y mañana tiene que trabajar contra Postgres desde .NET. Qué cambia de nombre, qué cambia de verdad y qué te va a morder si no lo sabés.

    Está pensada para leerse de corrido una vez y después volver a los capítulos puntuales. Cada tema compara lo que hacías en SQL Server con lo que se hace en PostgreSQL. Todos los bloques marcados "PostgreSQL" se extraen de esta misma página y se ejecutan, en orden, contra un PostgreSQL 16 real cada vez que se publica; si la guía dice que algo devuelve 3, es porque devolvió 3. Los bloques de SQL Server son de referencia (no hay un SQL Server en la nube donde corre esto).

    Índice

      Capítulo 1El mapa mental: instancia, base, esquema y conexión

      En SQL Server te conectás a una instancia y después hacés USE Ventas para elegir la base. Podés hacer SELECT * FROM Otra.dbo.Clientes y cruzar bases en una misma consulta. En PostgreSQL eso no existe: la conexión es a una base concreta, no hay USE, y las otras bases del mismo servidor (el cluster) son invisibles salvo que montes una extensión como postgres_fdw o dblink. Si en SQL Server tenías tres bases que se hablan entre sí, en Postgres eso suele ser una base con tres esquemas.

      El esquema public es el dbo de Postgres: donde caen las tablas si no decís otra cosa. Qué esquemas se buscan y en qué orden lo decide search_path, una variable de sesión. Los nombres se califican igual: esquema.tabla.

      -- Toda la guía trabaja en un esquema propio para no ensuciar nada.
DROP SCHEMA IF EXISTS guia CASCADE;
CREATE SCHEMA guia;
SET search_path TO guia, public;

-- Esto es lo más parecido a "SELECT DB_NAME(), SCHEMA_NAME(), SUSER_NAME()":
SELECT current_database(), current_schema(), current_user, version();

      Capítulo 2Mayúsculas, comillas y la trampa de "Clientes"

      Esta es la primera sorpresa de todo el que viene de SQL Server. En Postgres, los identificadores sin comillas se pasan a minúsculas. CREATE TABLE Clientes crea una tabla llamada clientes, y SELECT * FROM CLIENTES la encuentra porque también se baja a minúsculas. Hasta ahí, inofensivo. El problema aparece con las comillas dobles: CREATE TABLE "Clientes" crea una tabla que se llama exactamente Clientes, y a partir de ahí hay que escribirla con comillas siempre.

      CREATE TABLE Clientes (Id int, Nombre text);     -- se llama clientes, columnas id y nombre
CREATE TABLE "Clientes" (Id int, "Nombre" text);  -- otra tabla distinta, "Clientes" con columna id y columna "Nombre"

SELECT table_name FROM information_schema.tables WHERE table_schema = 'guia' ORDER BY 1;
-- → Clientes
-- → clientes

SELECT nombre FROM clientes;        -- anda
SELECT "Nombre" FROM "Clientes";    -- anda
-- SELECT Nombre FROM "Clientes";   -- falla: busca la columna "nombre" y la tabla tiene "Nombre"
DROP TABLE "Clientes"; DROP TABLE clientes;

      Por qué te importa desde .NET: EF Core con Npgsql pone comillas a todo lo que genera. Si dejás las convenciones por defecto, tu entidad Cliente termina en una tabla "Clientes" con columnas "FechaAlta", y cada vez que alguien abra psql y escriba select fechaalta from clientes va a recibir relation "clientes" does not exist. La convención del ecosistema es snake_case en minúsculas, y hay un paquete que se encarga solo:

      // dotnet add package EFCore.NamingConventions
services.AddDbContext<VentasContext>(o => o
    .UseNpgsql(connectionString)
    .UseSnakeCaseNamingConvention());   // Cliente.FechaAlta → cliente.fecha_alta

      Comparar texto: acá sí importa la mayúscula

      La segunda sorpresa. En SQL Server la collation por defecto suele ser _CI_AS: 'Nico' = 'nico' es verdadero y WHERE email = 'A@B.COM' encuentra a@b.com. En Postgres la comparación es sensible a mayúsculas por defecto, en =, en LIKE, en GROUP BY y en los índices únicos.

      SELECT 'Nico' = 'nico' AS iguales, 'Nico' ILIKE 'nico' AS iguales_ilike;
-- → false | true
SELECT lower('Nico') = lower('nico');   -- → true: la forma habitual

-- Para un email único sin importar mayúsculas: índice sobre una expresión
CREATE TABLE usuario (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, email text NOT NULL);
CREATE UNIQUE INDEX usuario_email_unico ON usuario (lower(email));
INSERT INTO usuario (email) VALUES ('Nico@Ejemplo.com');
-- INSERT INTO usuario (email) VALUES ('nico@ejemplo.com');  -- falla: duplicate key
SELECT * FROM usuario WHERE lower(email) = lower('NICO@ejemplo.com');  -- usa el índice

      Opciones, de la más usada a la menos:

      • lower() en los dos lados y un índice sobre lower(columna). Simple, rápido, universal.
      • ILIKE para búsquedas tipo LIKE sin importar mayúsculas. No usa el índice común; con pg_trgm y un índice GIN sí.
      • El tipo citext (extensión incluida en la distribución): una columna que se compara sin distinguir mayúsculas en todas partes. Cómodo, pero es un tipo distinto y EF Core necesita que lo mapees (HasColumnType("citext")).
      • Collations no determinísticas (desde Postgres 12): CREATE COLLATION ci (provider = icu, locale = 'und-u-ks-level2', deterministic = false). Es lo más parecido a _CI, pero en 16 LIKE no funciona sobre esas columnas y hay otras limitaciones. Para casos puntuales, no para toda la base.
      Ojo: los identificadores se cortan a 63 caracteres. Si tu convención genera ix_detalle_de_pedido_fecha_de_entrega_estimada_cliente_sucursal_id (68), Postgres lo trunca, avisa con un NOTICE que nadie lee, y dos índices distintos pueden terminar con el mismo nombre.

      Ojo con la precisión de las fechas: SQL Server guarda datetime2 con 100 ns y .NET DateTime también. Postgres guarda microsegundos. Un DateTime.UtcNow que guardás y volvés a leer no es igual al original (Ticks distinto). Los tests que comparan fechas con Assert.Equal después de un round-trip fallan; compará con tolerancia o truncá antes de guardar.

      Capítulo 4Identidad, secuencias y RETURNING

      IDENTITY(1,1) se escribe GENERATED ALWAYS AS IDENTITY (desde Postgres 10; serial es la forma vieja y hoy se desaconseja). Por debajo hay una secuencia, que es un objeto aparte y se puede consultar o reiniciar. Igual que en SQL Server, un rollback no devuelve el número: los huecos son normales.

      Lo que cambia para mejor es SCOPE_IDENTITY() y OUTPUT: en Postgres cualquier INSERT, UPDATE o DELETE puede terminar en RETURNING y devolver las filas afectadas, con las columnas que quieras, calculadas o no.

      INSERT INTO Pedido (ClienteId, Total)
OUTPUT inserted.Id, inserted.Numero
VALUES (1, 200);

-- o la forma vieja
INSERT INTO Pedido (ClienteId, Total) VALUES (1, 200);
SELECT SCOPE_IDENTITY();
      INSERT INTO pedido (cliente_id, total)
VALUES (1, 200)
RETURNING id, numero, creado_en;

-- también en UPDATE y DELETE
UPDATE pedido SET pagado = true WHERE id = 2
RETURNING id, total * 1.21 AS total_con_iva;
      -- Reiniciar una identidad (DBCC CHECKIDENT) y ver el último valor
ALTER TABLE pedido ALTER COLUMN id RESTART WITH 1000;
INSERT INTO pedido (cliente_id, total) VALUES (1, 10) RETURNING id;   -- → 1000
SELECT pg_get_serial_sequence('pedido', 'id');                       -- → guia.pedido_id_seq

-- ALWAYS no deja insertar el id a mano; BY DEFAULT sí (útil al migrar datos con ids existentes)
-- INSERT INTO pedido (id, cliente_id, total) VALUES (5, 1, 1);  -- falla con GENERATED ALWAYS
INSERT INTO pedido (id, cliente_id, total) OVERRIDING SYSTEM VALUE VALUES (5, 1, 1);
      TRUNCATE no reinicia la identidad salvo que lo pidas: TRUNCATE pedido RESTART IDENTITY. En SQL Server la reinicia siempre. Y TRUNCATE es transaccional en los dos motores, así que se puede hacer rollback.

      Sobre los GUID como clave primaria: en Postgres uuid ocupa 16 bytes y se indexa bien, pero gen_random_uuid() genera v4 (aleatorios), que fragmentan el índice igual que NEWID(). El equivalente de NEWSEQUENTIALID() es un UUID v7 (ordenado por tiempo): en .NET 9 tenés Guid.CreateVersion7() para generarlo del lado de la aplicación, y Postgres 18 trae uuidv7() en el motor.

      En UPDATE … FROM no repitas la tabla destino en el FROM. En T-SQL se escribe UPDATE p … FROM Pedido p JOIN …; si en Postgres ponés UPDATE pedido SET … FROM pedido p JOIN … hiciste un producto cartesiano de la tabla consigo misma y actualizaste todo.

      El upsert idiomático es INSERT … ON CONFLICT. MERGE existe desde Postgres 15 con la sintaxis estándar, pero ON CONFLICT es más corto, más viejo y, a diferencia del MERGE de SQL Server, es atómico frente a inserciones concurrentes de la misma clave.

-- → C3 | 1

      Listas de valores: adiós STRING_SPLIT y TVP, hola arrays

      El clásico "quiero pasar una lista de ids al query" se resuelve con un array como parámetro. Npgsql lo pasa nativo (un int[] de C# es un int[] de Postgres), así que no hay que concatenar nada ni armar un tipo de tabla.

-- Un array como tabla, con su posición
SELECT * FROM unnest(ARRAY['A1', 'B2']) WITH ORDINALITY AS t(sku, orden);

-- Y al revés: una columna como array
SELECT array_agg(sku ORDER BY sku) FROM stock;   -- → {A1,B2,C3}

      Cosas que no existen y cómo se dicen

      • SELECT … INTO Nueva FROM … funciona en Postgres, pero la forma recomendada es CREATE TABLE nueva AS SELECT …. En PL/pgSQL, SELECT INTO significa "asignar a una variable".
      • WITH (NOLOCK): no hay nada que poner. Las lecturas no bloquean ni se bloquean (capítulo 9).
      • TOP (n) en UPDATE/DELETE: DELETE FROM t WHERE id IN (SELECT id FROM t WHERE … LIMIT 1000).
      • PIVOT: la cláusula FILTER es más legible: count(*) FILTER (WHERE pagado) AS pagados. Para pivots dinámicos, la extensión tablefunc (crosstab).
      • DECLARE @x int = 5 en un script suelto: no hay variables fuera de PL/pgSQL. En psql, \set x 5 y :x; en scripts, un bloque DO $$ … $$ (capítulo 8).
      • IF OBJECT_ID('t') IS NOT NULL DROP TABLE t: DROP TABLE IF EXISTS t. También CREATE TABLE IF NOT EXISTS, CREATE OR REPLACE VIEW/FUNCTION.
      • WITH recursivo: hay que escribir WITH RECURSIVE. Si no, error.
      • @@ROWCOUNT: en PL/pgSQL, GET DIAGNOSTICS n = ROW_COUNT. Desde .NET, el ExecuteNonQuery te lo devuelve igual.
      • sp_rename: ALTER TABLE t RENAME COLUMN a TO b. Cambiar tipo: ALTER TABLE t ALTER COLUMN a TYPE bigint USING a::bigint.
      • TRY_CAST: no hay. Desde la 16, pg_input_is_valid(texto, 'tipo') permite escribir CASE WHEN pg_input_is_valid(s, 'int') THEN s::int END.

-- → 12 | 12 ; abc | NULL ; '' | NULL
WITH RECURSIVE numeros AS (SELECT 1 AS n UNION ALL SELECT n + 1 FROM numeros WHERE n < 5)
SELECT string_agg(n::text, ',') FROM numeros;   -- → 1,2,3,4,5
SELECT * FROM generate_series(1, 5) AS n;        -- la tabla de números que siempre terminabas creando a mano

      Capítulo 6Fechas, zonas horarias y Npgsql

      Este capítulo existe porque es, lejos, el lugar donde más equipos .NET se traban al pasar a Postgres. Hay dos tipos de timestamp y conviene entender exactamente qué guarda cada uno:

      • timestamp (sin zona, timestamp without time zone): una hora de pared, sin saber de dónde. "2026-10-12 03:00". Es el datetime2 de siempre. Ideal para "el turno es a las 15:00" o para fechas de calendario.
      • timestamptz (timestamp with time zone): un instante. Se guarda normalizado a UTC y, al leerlo, se muestra en la zona horaria de la sesión (SHOW TimeZone). No guarda la zona ni el offset original, a diferencia de datetimeoffset. Si necesitás saber "en qué zona estaba el usuario", eso va en otra columna.
      SET TimeZone = 'America/Argentina/Buenos_Aires';     -- Argentina es -03 todo el año, sin horario de verano
SELECT TIMESTAMPTZ '2026-10-12 03:00:00-03' AS instante,
       TIMESTAMPTZ '2026-10-12 03:00:00-03' AT TIME ZONE 'UTC' AS hora_de_pared_en_utc,
       TIMESTAMPTZ '2026-10-12 03:00:00-03' AT TIME ZONE 'Europe/Madrid' AS hora_de_pared_en_madrid;
-- → 2026-10-12 03:00:00-03 | 2026-10-12 06:00:00 | 2026-10-12 08:00:00

-- "AT TIME ZONE" convierte en los dos sentidos:
--   timestamptz AT TIME ZONE 'zona' → timestamp (la hora de pared en esa zona)
--   timestamp   AT TIME ZONE 'zona' → timestamptz (interpreta la hora de pared como de esa zona)
SELECT (TIMESTAMP '2026-10-12 03:00' AT TIME ZONE 'America/Argentina/Buenos_Aires') = TIMESTAMPTZ '2026-10-12 06:00:00+00';  -- → true

-- Agrupar por día "argentino" un campo guardado como instante:
SELECT date_trunc('day', creado_en AT TIME ZONE 'America/Argentina/Buenos_Aires')::date AS dia, count(*) FROM pedido GROUP BY 1 ORDER BY 1;
RESET TimeZone;

      Qué hace Npgsql con DateTime

      Desde Npgsql 6 (2021) el mapeo es estricto, y es el que te va a hacer renegar la primera semana:

      • DateTime con Kind = Utc → timestamptz. Al leer un timestamptz, siempre te devuelve Kind = Utc.
      • DateTime con Kind = Unspecified → timestamp. Al leer un timestamp, Kind = Unspecified.
      • DateTime con Kind = Local escrito en una columna timestamptz → excepción: Cannot write DateTime with Kind=Local to PostgreSQL type 'timestamp with time zone', only UTC is supported. Y lo mismo con Unspecified. Esto ocurre al guardar DateTime.Now, al parsear un "2026-10-12T03:00" sin zona, o al leer una fecha de un DTO de entrada.
      • DateTimeOffset → timestamptz, pero solo con offset cero; cualquier otro offset lanza la misma excepción. Al leer, viene con offset 0.
      // Lo correcto: trabajar en UTC adentro, convertir en los bordes.
pedido.CreadoEn = DateTime.UtcNow;                                  // Kind = Utc → timestamptz ✔
pedido.CreadoEn = DateTime.Now;                                     // Kind = Local → excepción ✘
pedido.CreadoEn = DateTime.SpecifyKind(dto.Fecha, DateTimeKind.Utc); // si SABÉS que el DTO viene en UTC

      Capítulo 9Transacciones, MVCC y bloqueos

      Las dos bases usan READ COMMITTED por defecto, pero la implementación es distinta y eso cambia la vida diaria. SQL Server (sin READ_COMMITTED_SNAPSHOT) usa bloqueos: un UPDATE sin confirmar frena a los SELECT que pasan por esa fila, y de ahí la costumbre del NOLOCK. Postgres es MVCC puro: cada transacción ve una foto consistente y las lecturas nunca bloquean a las escrituras ni al revés. Las escrituras sobre la misma fila sí se esperan entre sí, como en todos lados.

      Consecuencias prácticas:

      • NOLOCK no tiene equivalente ni falta hace. READ UNCOMMITTED se acepta por compatibilidad y se comporta como READ COMMITTED.
      • REPEATABLE READ en Postgres es un snapshot de toda la transacción (lo que en SQL Server llamás SNAPSHOT). SERIALIZABLE es serializabilidad real (SSI), sin bloqueos de rango: en lugar de esperar, falla con 40001 serialization_failure y el cliente tiene que reintentar.
      • Los deadlocks existen igual (error 40P01). Se detectan al segundo (deadlock_timeout) y se mata a una de las dos transacciones.
      • No hay lock escalation: un UPDATE de un millón de filas toma un millón de locks de fila, sin pasar a bloquear la tabla.

      La regla que más sorprende: un error aborta toda la transacción

      En SQL Server, con XACT_ABORT OFF (el default), si un statement falla dentro de una transacción los demás siguen y podés hacer COMMIT de lo que anduvo. En Postgres no: después de cualquier error, la transacción queda en estado abortado y cualquier otra orden responde current transaction is aborted, commands ignored until end of transaction block. Solo se puede hacer ROLLBACK, o volver a un SAVEPOINT previo.

      BEGIN;
INSERT INTO stock (sku, cantidad) VALUES ('D4', 1);
SAVEPOINT antes_del_dudoso;
INSERT INTO stock (sku, cantidad) VALUES ('D4', 1);      -- falla: duplicate key. La transacción queda abortada.
ROLLBACK TO SAVEPOINT antes_del_dudoso;                  -- se recupera hasta acá; D4 sigue insertado
INSERT INTO stock (sku, cantidad) VALUES ('E5', 1);      -- anda
COMMIT;
SELECT sku FROM stock WHERE sku IN ('D4', 'E5') ORDER BY 1;   -- → D4, E5

      Capítulo 10Índices, planes y EXPLAIN

      Tres diferencias estructurales, y después las herramientas:

      • No hay índice clustered. Toda tabla es un heap; la clave primaria es un índice B-tree común que apunta a la fila por su posición física (ctid). Existe el comando CLUSTER, pero reordena la tabla una sola vez y no la mantiene. Esto también significa que el orden físico no es el de la PK y que un SELECT sin ORDER BY devuelve cualquier cosa, incluso cambiando entre ejecuciones.
      • Hay más tipos de índice: B-tree (el de siempre), GIN (para jsonb, arrays, full text y trigramas), GiST y SP-GiST (geometría, rangos, vecinos más cercanos), BRIN (tablas enormes ordenadas por fecha, con índices diminutos), hash.
      • Los índices sobre expresiones y los parciales son de primera clase: ON (lower(email)), ON (fecha) WHERE estado = 'pendiente'. Los índices filtrados de SQL Server existen, pero los de expresión requerían columnas calculadas persistidas.

      Cosas que hay que desaprender:

      • Un Seq Scan no es un bug. En tablas chicas, o cuando la consulta trae una parte grande de la tabla, es lo correcto. Con tablas de pocas páginas el planificador nunca va a usar tu índice, y está bien.
      • No hay hints (OPTION (RECOMPILE), FORCESEEK…). Se trabaja con estadísticas (ALTER TABLE … ALTER COLUMN … SET STATISTICS 1000, CREATE STATISTICS para correlaciones entre columnas), reescribiendo la consulta o, en última instancia, con la extensión pg_hint_plan.
      • Los index-only scans dependen del visibility map, que mantiene VACUUM. Una tabla con muchas escrituras recientes puede tener un índice cubriente perfecto y aun así ir al heap ("Heap Fetches" alto en el plan).
      • Query Store se llama pg_stat_statements: hay que agregarlo a shared_preload_libraries y hacer CREATE EXTENSION, y después tenés tiempo total, llamadas, filas y buffers por consulta normalizada. Es lo primero que se mira en cualquier base lenta.
      • count(*) sobre una tabla grande es lento (hay que visitar las filas por MVCC). Para un número aproximado: SELECT reltuples::bigint FROM pg_class WHERE relname = 'pedido'.

      Capítulo 11VACUUM: el concepto que no tenía equivalente

      En MVCC, un UPDATE no modifica la fila: escribe una versión nueva y deja la vieja marcada como muerta, para que las transacciones que todavía la ven sigan viéndola. Un DELETE tampoco libera espacio: marca. Alguien tiene que pasar después a recolectar esas versiones muertas, y ese alguien es VACUUM. Lo corre solo el proceso autovacuum, por tabla, cuando el porcentaje de filas muertas supera un umbral (20 % por defecto, demasiado alto para tablas grandes).

      Qué hace: marca el espacio como reutilizable (no lo devuelve al sistema operativo; eso es VACUUM FULL, que bloquea la tabla y reescribe todo), actualiza el visibility map (capítulo 10), y protege contra el wraparound del contador de transacciones (un tema de 32 bits que, si se descuida durante meses, para la base; autovacuum lo evita solo mientras lo dejes correr). VACUUM ANALYZE además actualiza estadísticas.

      -- Cuántas filas muertas hay y cuándo pasó autovacuum por última vez
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables WHERE schemaname = 'guia' ORDER BY n_dead_tup DESC;

-- A mano (no bloquea lecturas ni escrituras normales)
VACUUM (ANALYZE, VERBOSE) pedido;

-- Una tabla con mucho churn merece su propia configuración, más agresiva que la global
ALTER TABLE trabajo SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_threshold = 1000);

      Qué lo frena: transacciones largas (incluidas las idle in transaction), slots de replicación abandonados y prepared transactions huérfanas. Si una tabla crece sin parar aunque borres filas (bloat), lo primero es mirar pg_stat_activity por la transacción más vieja. En SQL Server el equivalente más cercano era el version store de tempdb con RCSI activado, pero nunca tuviste que pensar en esto. Acá sí: un día al menos, para entender por qué, y después dejar que autovacuum trabaje.

      Capítulo 13Paginación, texto libre y otras cosas útiles

      Paginación

      OFFSET … FETCH funciona igual (y LIMIT … OFFSET es lo mismo, más corto) y tiene el mismo problema: la página 500 lee y descarta 499 páginas. La alternativa es la paginación por cursor (keyset), y Postgres la hace cómoda porque compara tuplas: (a, b) < (x, y) es una comparación lexicográfica real que usa el índice compuesto.

      -- Página "siguiente" después del último elemento que vio el cliente (creado_en, id)
SELECT id, creado_en, total
FROM pedido
WHERE (creado_en, id) < (TIMESTAMPTZ '2030-01-01', 9223372036854775807)   -- los valores de la última fila de la página anterior
ORDER BY creado_en DESC, id DESC
LIMIT 20;
-- El índice que lo hace instantáneo: (creado_en DESC, id DESC), o el de cliente_id + creado_en si filtrás por cliente.

      Otras que valen la pena

      • DDL transaccional completo: BEGIN; CREATE TABLE …; ALTER TABLE …; ROLLBACK; deja todo como estaba. Las migraciones de EF Core corren cada una en una transacción: o entra todo o nada (salvo CREATE INDEX CONCURRENTLY).
      • DISTINCT ON: "la última fila de cada grupo" sin ROW_NUMBER(): SELECT DISTINCT ON (cliente_id) * FROM pedido ORDER BY cliente_id, creado_en DESC.
      • Columnas generadas (GENERATED ALWAYS AS (…) STORED): las computed columns persistidas.
      • Restricciones de exclusión: "dos reservas de la misma sala no pueden solaparse" como constraint, con rangos: EXCLUDE USING gist (sala WITH =, durante WITH &&).
      • LISTEN/NOTIFY: notificaciones push desde la base a las conexiones que escuchan, algo que en SQL Server requería Service Broker o SqlDependency. Npgsql las expone con el evento Notification.
      • Particionado declarativo (PARTITION BY RANGE (creado_en)) sin esquemas de partición ni funciones aparte.
      • COPY para cargas masivas: el BULK INSERT / bcp. Desde .NET, SqlBulkCopy se reemplaza por conn.BeginBinaryImport("COPY tabla (a, b) FROM STDIN (FORMAT BINARY)").

      Capítulo 14Roles, permisos y conexiones

      En Postgres no hay logins y usuarios separados: hay roles. Un rol con el atributo LOGIN puede conectarse; un rol sin él funciona como grupo, y los roles se pueden otorgar a otros roles. Los permisos se dan con GRANT por objeto, y hay un detalle que a todos se les pasa la primera vez: para ver una tabla hace falta también USAGE sobre su esquema, y los GRANT no se aplican a tablas futuras salvo que uses ALTER DEFAULT PRIVILEGES.

      CREATE ROLE lectores;                                       -- grupo, sin login
CREATE ROLE app_ventas LOGIN PASSWORD 'cambiame' IN ROLE lectores;   -- usuario de la aplicación
GRANT USAGE ON SCHEMA guia TO lectores;
GRANT SELECT ON ALL TABLES IN SCHEMA guia TO lectores;      -- las que existen hoy
ALTER DEFAULT PRIVILEGES IN SCHEMA guia GRANT SELECT ON TABLES TO lectores;   -- las que se creen después
GRANT INSERT, UPDATE, DELETE ON pedido, stock TO app_ventas;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA guia TO app_ventas;   -- sin esto, los INSERT con identidad fallan

-- Qué puede hacer quién
SELECT grantee, table_name, string_agg(privilege_type, ', ' ORDER BY privilege_type)
FROM information_schema.role_table_grants WHERE table_schema = 'guia' AND grantee IN ('lectores', 'app_ventas') GROUP BY 1, 2 ORDER BY 1, 2;

      Dos cosas más que no están en SQL:

      • pg_hba.conf decide quién puede conectarse desde dónde y cómo se autentica (por rol, base, IP y método: scram-sha-256, certificado, trust…). Es el equivalente de la configuración de autenticación de la instancia más las reglas de firewall, en un archivo de texto. Un "no puedo conectarme" nuevo casi siempre es esto.
      • Row Level Security existe en los dos. En Postgres: ALTER TABLE t ENABLE ROW LEVEL SECURITY más CREATE POLICY … USING (tenant_id = current_setting('app.tenant')::int). Para multi-tenant, es una forma seria de que una consulta sin WHERE no filtre datos ajenos.

      Sobre las conexiones: Postgres crea un proceso por conexión, y max_connections suele ser 100. SQL Server maneja miles de conexiones baratas; acá no. El pool de Npgsql (que viene activado) alcanza para una aplicación; con muchas réplicas o funciones serverless hace falta un pooler del lado del servidor como PgBouncer. Y las estadísticas de bloqueo del capítulo 9 valen el doble: una conexión bloqueada es un proceso ocupado.

      Qué cambia en el modelo de EF Core

      • Identidad: por defecto genera GENERATED BY DEFAULT AS IDENTITY. Nada que hacer. Si venís con HasDefaultValueSql("NEWID()"), pasa a "gen_random_uuid()"; GETUTCDATE() a "now()".
      • Concurrencia optimista: [Timestamp] byte[] RowVersion no existe. Se usa la columna de sistema xmin: modelBuilder.Entity<Pedido>().Property<uint>("xmin").IsRowVersion() (sin columna real) o una propiedad uint Version con IsRowVersion().
      • Fechas: DateTime → timestamp with time zone por defecto. Todo lo del capítulo 6 aplica. DateOnly/TimeOnly se mapean nativos.
      • Strings: string → text. HasMaxLength(100) → varchar(100). No hay IsUnicode(false) que cambie nada.
      • Arrays y JSON: List<string> o string[] van a text[] solos, y Contains en LINQ se traduce a = ANY(…) o @>. Las entidades propias con ToJson() van a jsonb.
      • Esquemas y extensiones: modelBuilder.HasDefaultSchema("ventas"), modelBuilder.HasPostgresExtension("pg_trgm") (lo crea la migración).
      • Migraciones: el SQL generado es distinto, así que las migraciones existentes de SQL Server no sirven: se borran y se genera una inicial contra Postgres. CREATE INDEX CONCURRENTLY no puede ir dentro de la transacción de la migración; para tablas grandes se hace aparte.
      • Consultas crudas: FromSqlInterpolated($"… WHERE id = {id}") sigue siendo seguro y parametriza. Los nombres de tabla y columna hay que escribirlos como quedaron (minúsculas con snake_case si seguiste el consejo; con comillas y PascalCase si no).

      CierreLas diez cosas que te van a sorprender, en orden de aparición

      1. Los nombres sin comillas van a minúsculas, y EF Core pone comillas: elegí snake_case el primer día (cap. 2).
      2. 'Nico' = 'nico' es falso. Mayúsculas y minúsculas importan en todos lados (cap. 2).
      3. No podés cruzar bases en una consulta. Una base, varios esquemas (cap. 1).
      4. DateTime.Now en una columna timestamptz explota. Todo en UTC adentro (cap. 6).
      5. Un error cualquiera aborta la transacción entera hasta el ROLLBACK (cap. 9).
      6. Los NULL se ordenan al final, y en un UNIQUE caben varios (cap. 7).
      7. No hay NOLOCK porque no hace falta, y no hay índice clustered porque todo es heap (caps. 9 y 10).
      8. now() es la hora del BEGIN, no la de ahora (cap. 5).
      9. Las fechas pierden los nanosegundos: los tests de round-trip con Assert.Equal fallan (cap. 3).
      10. Existe VACUUM, y una transacción abierta y ociosa lo frena para toda la base (cap. 11).

      Y, para compensar, las cinco que vas a extrañar cuando vuelvas a SQL Server: RETURNING, los arrays como parámetros, jsonb con índices, DISTINCT ON y el DDL transaccional.
