    Índices con el cronómetro en la mano

    Trece experimentos sobre índices de SQL Server, medidos en páginas leídas y milisegundos contra un servidor de verdad. Para gente que escribe consultas desde .NET y quiere saber qué pasa del otro lado.

    SQL Server 2022 (Developer, Linux, 4 CPU) · base de ejemplo «Tienda»: 400.000 pedidos, 1,2 millones de ítems, 50.000 clientes · todos los números salen de resultados.json, generado con experimentos.sql. Si querés ver cualquiera de estos planes explicado, está Plan en criollo.

    Índice

      Antes de empezarPor qué contar páginas y no segundos

      Cuando una consulta tarda, lo primero que uno mira es cuánto tarda. Es lo peor que se puede mirar: el tiempo depende de si los datos estaban en memoria, de qué más corría en ese momento, de la red, del cliente que consume las filas. La misma consulta da 20 ms y después 300 ms sin que nada haya cambiado en ella.

      Lo que sí es estable es cuántas páginas de 8 KB tuvo que leer el motor para contestar. SQL Server lo llama lecturas lógicas (logical reads) y lo informa con SET STATISTICS IO ON o dentro del plan de ejecución real. Una consulta que lee 19 páginas es rápida en cualquier servidor; una que lee 300.000 es lenta en cualquier servidor, aunque hoy le haya tocado todo en caché.

      Así que este escrito mide en páginas. El tiempo se anota al lado, con la salvedad de que es el de un contenedor sin carga y con todo en memoria: sirve para comparar entre experimentos, no como promesa.

      La base de ejemplo

      Una tienda: Clientes (50.000), Productos (2.000), Pedidos (400.000, con un mayorista, el cliente 1, que tiene 100.000) e Items (1.200.000). Pedidos arranca con dos índices: la clave primaria agrupada PK_Pedidos sobre PedidoId y un no agrupado IX_Pedidos_ClienteId sobre ClienteId. Cada capítulo crea lo que necesita y lo borra al final, así que los experimentos son independientes. El script completo, incluida la carga de datos, está en experimentos.sql.

      Cada consulta «medida» se corrió dos veces y se anotó la segunda (caché caliente), con SET STATISTICS XML ON, que devuelve el plan real con las lecturas y el tiempo por operador.

      Capítulo 1La página y el cronómetro

      Empecemos por saber cuánto ocupa lo que vamos a leer. sys.dm_db_index_physical_stats describe el índice agrupado de Pedidos nivel por nivel:

      NivelPáginasRegistrosBytes por registroLleno
      0 (hojas: las filas)10.001400.00019999,3 %
      1 (intermedio)3610.0011144,6 %
      2 (raíz)136115,8 %

      Un árbol de tres niveles: una raíz, 36 páginas intermedias y 10.001 hojas donde viven las 400.000 filas, a 199 bytes y 40 filas por página. De acá sale un número que vamos a usar todo el tiempo: llegar a una fila por su clave cuesta 3 lecturas (raíz, intermedio, hoja). Y otro: leer la tabla entera cuesta unas 10.000.

      SELECT SUM(Total) FROM dbo.Pedidos;     -- tres veces seguidas
      CorridaLecturasTiempoPlan
      1.ª10.47117 msClustered Index Scan
      2.ª10.47116 msClustered Index Scan
      3.ª10.47118 msClustered Index Scan

      Las lecturas no se mueven; el tiempo baila. Y una sorpresa chica: SELECT COUNT(*) sobre la misma tabla lee 700 páginas, no 10.471. El motor no cuenta sobre la tabla sino sobre el índice más angosto que tenga (IX_Pedidos_ClienteId, 704 páginas), porque cualquier índice tiene exactamente una entrada por fila. Primera regla: cuanto menos bytes por fila tiene lo que se lee, menos páginas hay que leer. Todo lo que sigue es variaciones de eso.

      Qué me llevo

      • Medí en lecturas lógicas, no en milisegundos. Es lo que se puede comparar antes y después de un cambio.
      • Una fila por clave: 3 lecturas. La tabla entera: una lectura por página (~10.000 acá).
      • El motor elige el índice más chico que tenga las columnas que hacen falta.

      Capítulo 2Heap o índice agrupado

      Una tabla sin índice agrupado es un heap: las filas están donde cayeron. Copiamos Pedidos a un heap con SELECT * INTO dbo.PedidosHeap y buscamos un pedido por su id en las dos:

      SELECT PedidoId, Total FROM dbo.PedidosHeap WHERE PedidoId = 123456;
SELECT PedidoId, Total FROM dbo.Pedidos     WHERE PedidoId = 123456;
      TablaLecturasTiempoPlan
      Heap10.00517 msTable Scan (paralelo)
      Con índice agrupado30 msClustered Index Seek

      Sin índice, el único modo de encontrar un id es leer todo. Esto es lo que pasa en cada tabla «temporal» o de staging que se crea sin clave y después se consulta por un campo.

      Ahora le creamos al heap un índice no agrupado sobre ClienteId, como el que tiene Pedidos, y buscamos los pedidos de un cliente con 5:

      TablaLecturasPlanPáginas del índice
      Heap8Index Seek + RID Lookup ×5902
      Con índice agrupado19Index Seek + Key Lookup ×5704

      Dos cosas honestas. Primera: el RID Lookup es más barato por fila que el Key Lookup (1 lectura contra 3), porque el índice del heap guarda la dirección física de la fila y no hay que bajar por un árbol. Segunda: el índice sobre el heap es un 28 % más grande, porque esa dirección (RID) ocupa 8 bytes y el int de la clave agrupada 4.

      ¿Entonces por qué todo el mundo recomienda índice agrupado? Porque el heap no tiene orden: no sirve para rangos, para ORDER BY, para TOP, ni para que el optimizador sepa dónde empieza y termina nada; porque las actualizaciones que agrandan una fila la mudan y dejan un «forwarded record» que cuesta una lectura extra para siempre; y porque, como vimos arriba, cualquier búsqueda por un campo sin índice es la tabla entera. El RID Lookup barato es el premio consuelo.

      Qué me llevo

      • Toda tabla que se consulte por algo necesita un índice agrupado. Las tablas de staging y las temporales también, si se las va a buscar por un campo.
      • Un heap no es «más rápido para insertar» en ningún escenario que te importe desde una aplicación.

      Capítulo 3La clave agrupada viaja en todos los índices

      Cada entrada de un índice no agrupado lleva, además de sus columnas, la clave agrupada completa de la fila: es lo que usa el Key Lookup para llegar a la fila. Si la clave agrupada es ancha, todos los índices engordan. Para verlo, armamos PedidosCodigo: la misma tabla, pero con clave primaria agrupada sobre un código nvarchar(60) del estilo PED-20260914-0123456-4242 en lugar del int.

      ObjetoClave intClave nvarchar(60)Diferencia
      Índice agrupado (la tabla)10.039 páginas12.775 páginas+27 %
      Índice sobre ClienteId704 páginas3.197 páginas×4,5
      Buscar 5 pedidos de un cliente19 lecturas23 lecturas+4

      El índice sobre ClienteId pasa de 704 a 3.197 páginas sin que cambie su definición: cada entrada carga 50 caracteres de código en vez de 4 bytes. Multiplicá por la cantidad de índices de la tabla y por la cantidad de filas de una tabla de verdad.

      Lo mismo pasa con uniqueidentifier (16 bytes, y además aleatorio: en GUID o identity está medido qué le hace al llenado de páginas) y con claves compuestas de varias columnas. La clave agrupada ideal es angosta, única, creciente y que no cambie: un int o bigint identity casi siempre. El código de negocio va en un índice único aparte.

      Qué me llevo

      • La clave agrupada se copia en cada índice no agrupado: elegila angosta.
      • Un código, un GUID o una clave compuesta pueden ser la clave primaria «lógica», pero el índice agrupado conviene que sea un entero.

      Capítulo 4Selectividad y el punto de inflexión

      Un índice sobre una columna no garantiza que se use. Estado tiene cuatro valores con esta distribución:

      EstadoFilasPorcentaje
      1194.07348,5 %
      2194.10448,5 %
      33.9891,0 %
      47.8342,0 %

      Creamos IX_Pedidos_Estado sobre Estado y pedimos PedidoId, Total por estado. Como el índice no tiene Total, usarlo implica un Key Lookup por fila. Con hints forzamos cada camino para ver qué cuesta:

      SELECT PedidoId, Total FROM dbo.Pedidos WHERE Estado = 3;                     -- lo que elige el optimizador
SELECT PedidoId, Total FROM dbo.Pedidos WITH (FORCESEEK) WHERE Estado = 3;    -- obligado a usar el índice
SELECT PedidoId, Total FROM dbo.Pedidos WITH (FORCESCAN) WHERE Estado = 3;    -- obligado a leer todo
      FiltroCaminoLecturasTiempoPlan
      Estado = 3 (1 %, 3.989 filas)Lo que eligió10.54420 msClustered Index Scan
      Forzando el índice11.46012 msIndex Seek + Key Lookup ×3.989
      Estado = 1 (48 %, 194.073 filas)Lo que eligió10.039109 msClustered Index Scan
      Forzando el índice558.165249 msIndex Seek + Key Lookup ×194.073
      ClienteId = 4242 (5 filas)Lo que eligió190 msIndex Seek + Key Lookup ×5
      Forzando leer todo10.54416 msClustered Index Scan

      Con el 1 % de las filas, el optimizador prefirió leer toda la tabla, y tenía razón por poco: 3.989 lookups a 3 lecturas cada uno son 11.460, más que las 10.544 del recorrido. Con el 48 % ni se discute: 558.165 lecturas, 55 veces la tabla. Con 5 filas, el índice gana por 500 a 1.

      Ese es el punto de inflexión (tipping point): como cada lookup cuesta más o menos lo que cuesta leer una página entera, el índice deja de convenir cuando la cantidad de filas que devuelve se acerca a la cantidad de páginas de la tabla; en la práctica, entre el 0,5 % y el 2 % de las filas. No depende de la cantidad de valores distintos de la columna, depende de cuántas filas devuelve esta consulta. Un índice sobre Estado sirve para buscar los pendientes (1 %) y no sirve para buscar los entregados (48 %), y las dos consultas pueden ser la misma con otro parámetro. Lo que anuló al índice no fue la columna: fue el lookup. Y eso tiene arreglo.

      Qué me llevo

      • Un índice que obliga a buscar el resto de la fila deja de servir cerca del 1 % de las filas.
      • Si el optimizador elige un scan teniendo un índice, antes de forzarlo con hints mirá cuántas filas devuelve el filtro.

      Capítulo 5El índice cubriente

      El problema del capítulo anterior es el viaje a la tabla por cada fila. Si el índice tiene todas las columnas que pide la consulta, no hay viaje: el índice la cubre. Las columnas que no se usan para buscar van en INCLUDE, que las guarda solo en las hojas y no las mete en el árbol.

      -- Antes: solo IX_Pedidos_ClienteId (ClienteId)
SELECT PedidoId, Fecha, Estado, Total FROM dbo.Pedidos WHERE ClienteId = 1;      -- el mayorista, 100.000 pedidos

CREATE INDEX IX_Pedidos_ClienteId_Cub ON dbo.Pedidos (ClienteId) INCLUDE (Fecha, Estado, Total);
      ConsultaÍndiceLecturasTiempoPlan
      ClienteId = 1 (100.000 filas)Sin cubrir, forzando el índice287.633154 msIndex Seek + Key Lookup ×100.000
      Sin cubrir, lo que eligió10.54480 msClustered Index Scan
      Cubriente37538 msIndex Seek, nada más
      ClienteId = 4242 (5 filas)Sin cubrir190 msIndex Seek + Key Lookup ×5
      Cubriente30 msIndex Seek
      SELECT * ... ClienteId = 4242Cubriente (pero pide todo)180 msIndex Seek + Key Lookup ×5

      Para el mayorista, el índice cubriente lee 375 páginas: 28 veces menos que el recorrido que el optimizador había elegido y 767 veces menos que el índice sin cubrir. Y ya no hay punto de inflexión: el índice sirve para 5 filas y para 100.000, porque cada fila está en el índice completa y contigua.

      La última fila de la tabla es la trampa de siempre: SELECT * pide Observaciones, que no está en el índice, y vuelve el Key Lookup. Un índice cubriente cubre una lista de columnas; cada columna de más en el SELECT puede romperlo. Es el argumento técnico contra SELECT * y contra cargar entidades enteras cuando se necesitan tres campos (en EF Core, .Select(p => new { p.PedidoId, p.Fecha, p.Total }) en lugar de traer el Pedido).

      El costo: el índice pasó de 704 a 1.499 páginas (las hojas ahora llevan tres columnas más) y cada INSERT y cada UPDATE de esas columnas lo mantiene. Capítulo 11.

      Qué me llevo

      • Si una consulta importa, su índice debería cubrirla: columnas del WHERE en la clave, las del SELECT en INCLUDE.
      • Pedí solo las columnas que usás. SELECT * y las entidades completas desarman el índice cubriente.
      • El índice cubriente elimina el punto de inflexión del capítulo 4.

      Capítulo 6El orden de las columnas

      Un índice sobre (A, B) está ordenado por A y, dentro de cada A, por B. Como una guía telefónica por apellido y nombre: sirve para buscar por apellido, o por apellido y nombre, pero no para buscar por nombre solo. Para la consulta «pedidos pendientes desde junio» creamos los dos órdenes posibles, con las mismas columnas incluidas:

      CREATE INDEX IX_EF ON dbo.Pedidos (Estado, Fecha) INCLUDE (ClienteId, Total);
CREATE INDEX IX_FE ON dbo.Pedidos (Fecha, Estado) INCLUDE (ClienteId, Total);

SELECT PedidoId, ClienteId, Fecha, Total FROM dbo.Pedidos WHERE Estado = 3 AND Fecha >= '2026-06-01';
      FiltroÍndiceLecturasPlan
      Estado = 3 AND Fecha >= junio (605 filas)(Estado, Fecha)6Index Seek: va al estado 3, y dentro, desde junio
      (Fecha, Estado)251Index Seek desde junio, y filtra el estado fila por fila
      Solo Fecha >= 15 de septiembre (8.760 filas)(Estado, Fecha)1.495Index Scan: Fecha no es la primera columna
      (Fecha, Estado)37Index Seek
      Solo Estado = 3 (3.989 filas)(Estado, Fecha)20Index Seek
      (Fecha, Estado)1.496Index Scan

      Para la consulta completa, (Estado, Fecha) lee 6 páginas y (Fecha, Estado) 251: con la igualdad primero, el rango queda contiguo; con el rango primero, el motor entra en junio y tiene que mirar el estado de cada pedido desde entonces. La regla: primero las columnas de igualdad, después la de rango; y de las de igualdad, primero la más selectiva si las consultas varían.

      Las otras cuatro filas muestran el otro lado: cada índice solo sirve para buscar si el filtro incluye su primera columna. Cuando no, el motor lo recorre entero (1.495 lecturas, igual que la tabla pero más chico) o lo ignora. Un índice sobre (Estado, Fecha) no reemplaza a uno sobre (Fecha).

      Qué me llevo

      • Igualdad antes que rango. WHERE Estado = @e AND Fecha >= @f quiere (Estado, Fecha).
      • La primera columna del índice tiene que estar en el WHERE; si no, el índice no busca.
      • Antes de crear un índice, mirá los que ya existen: a veces alcanza con agregar una columna al final o en INCLUDE.

      Capítulo 7Sargabilidad: cómo anular un índice sin querer

      Un predicado es «sargable» (de search argument) cuando el motor puede usarlo para ir directo a un rango del índice. Se rompe cuando la columna no queda sola de un lado de la comparación. Con IX_Pedidos_Fecha (Fecha) INCLUDE (Total), IX_Pedidos_Total (Total) y el IX_Clientes_Email (Email) que ya existía:

      Lo que se escribeLecturasPlan
      WHERE YEAR(Fecha) = 2026 AND MONTH(Fecha) = 91.246Index Scan: lee el índice entero y calcula YEAR y MONTH para cada fila
      WHERE Fecha >= '2026-09-01' AND Fecha < '2026-10-01'55Index Seek
      WHERE CAST(Fecha AS date) = '2026-09-15'7Index Seek (ver nota)
      WHERE Fecha >= '2026-09-15' AND Fecha < '2026-09-16'5Index Seek
      WHERE Email = N'cliente777@ejemplo.com.ar' (columna varchar, literal nvarchar)262Index Scan + aviso de conversión implícita
      WHERE Email = 'cliente777@ejemplo.com.ar'5Index Seek
      WHERE Email LIKE 'cliente777%'25Index Seek (prefijo: es un rango)
      WHERE Email LIKE '%777@%'360Index Scan
      WHERE Total * 1.21 > 6000946Index Scan
      WHERE Total > 6000 / 1.2112Index Seek

      Cuatro trampas, todas con el mismo arreglo: dejar la columna sola y mover la operación al otro lado. Las fechas se filtran por rango semiabierto (>= inicio, < fin), nunca por YEAR(), MONTH() ni BETWEEN con horas. Los cálculos se hacen sobre el parámetro, no sobre la columna. El LIKE solo busca si el patrón empieza con texto fijo; «contiene» recorre todo (para eso existe Full-Text Search, o una columna normalizada).

      Nota sobre CAST(Fecha AS date). Esa fila dio 7 lecturas y un seek: SQL Server sabe convertir CAST(col AS date) = @d en un rango. Pero estimó 1 fila donde había 542, porque no tiene estadísticas de la expresión. Con un join al lado, esa estimación errada es la que elige mal el plan. Preferí el rango explícito: anda igual de rápido y estima bien.

      La conversión implícita es la trampa de .NET. En C#, string viaja como nvarchar salvo que se diga lo contrario. Si la columna es varchar, el motor convierte la columna al tipo del parámetro (porque nvarchar tiene más precedencia) y el índice deja de servir para buscar: 262 lecturas contra 5, y en una tabla grande es la tabla entera. Arreglos: en Dapper, new DbString { Value = email, IsAnsi = true, Length = 200 }; en EF Core, .IsUnicode(false) o HasColumnType("varchar(200)") en la configuración de la propiedad; en ADO.NET, SqlDbType.VarChar. O usar nvarchar en la columna, que es lo que hace EF por defecto cuando crea el esquema.

      Qué me llevo

      • La columna sola de un lado; funciones y cuentas, del otro.
      • Fechas: >= desde AND < hasta. Nunca YEAR(), MONTH() ni CAST sobre la columna.
      • Si la columna es varchar, el parámetro tiene que ser varchar. Buscá «CONVERT_IMPLICIT» en los planes.
      • LIKE 'algo%' usa el índice; LIKE '%algo%' no.

      Capítulo 8ORDER BY, TOP y paginación

      Un índice también es un orden. «Los últimos 50 pedidos» sin índice sobre Fecha obliga a leer y ordenar los 400.000 para quedarse con 50; con índice, se leen 50 desde el final:

      SELECT TOP (50) PedidoId, Fecha, Total FROM dbo.Pedidos ORDER BY Fecha DESC;
      SituaciónLecturasTiempoPlan
      Sin índice sobre Fecha10.54437 msClustered Index Scan → Sort (Top N) → Top
      Con IX_Pedidos_Fecha (Fecha) INCLUDE (Total)30 msIndex Scan hacia atrás, 50 filas → Top

      Ahora paginemos esa lista con OFFSET … FETCH, que es lo que generan EF Core (Skip/Take) y casi todas las grillas:

      SELECT PedidoId, Fecha, Total FROM dbo.Pedidos
ORDER BY Fecha DESC, PedidoId DESC
OFFSET @saltar ROWS FETCH NEXT 50 ROWS ONLY;
      PáginaLecturasTiempoQué hizo
      OFFSET 0 (primera)30 msLeyó 50 filas del índice
      OFFSET 100.000 (página 2.001)31716 msLeyó 100.050 filas del índice y descartó 100.000
      OFFSET 350.000 (página 7.001)1.09274 msLeyó 350.050 filas y descartó 350.000
      Keyset: WHERE Fecha < @ultimaFecha + TOP 5030 msIndex Seek al punto exacto, 50 filas

      OFFSET no salta: lee y tira. Cada página es más cara que la anterior, y con un join o sin índice el costo se multiplica. La alternativa es la paginación por clave (keyset o «seek pagination»): en lugar de «saltá 350.000», «dame los 50 siguientes a la última fecha que mostré». El costo es constante en cualquier página. Se pierde el «ir a la página 7.001», que nadie usa; se gana que la página 7.001 no tumbe el servidor.

      -- Primera página
SELECT TOP (50) PedidoId, Fecha, Total FROM dbo.Pedidos ORDER BY Fecha DESC, PedidoId DESC;
-- Siguientes: con la (Fecha, PedidoId) de la última fila mostrada
SELECT TOP (50) PedidoId, Fecha, Total FROM dbo.Pedidos
WHERE Fecha < @ultimaFecha OR (Fecha = @ultimaFecha AND PedidoId < @ultimoId)
ORDER BY Fecha DESC, PedidoId DESC;

      En EF Core es .Where(p => p.Fecha < ultimaFecha).OrderByDescending(p => p.Fecha).ThenByDescending(p => p.PedidoId).Take(50). El índice tiene que coincidir con el ORDER BY completo, incluida la columna de desempate.

      Qué me llevo

      • Un índice cuyo orden coincide con el ORDER BY hace desaparecer el Sort y el TOP lee solo lo que devuelve.
      • OFFSET lee todo lo que salta. Para listas largas, paginación por clave.
      • El ORDER BY de una paginación necesita desempate (la clave) para ser determinista.

      Capítulo 9Índices filtrados y la trampa de los parámetros

      Si la consulta de siempre es «pendientes desde tal fecha» y los pendientes son el 1 %, no hace falta indexar el 99 % restante. Un índice con WHERE solo guarda las filas que cumplen la condición:

      CREATE INDEX IX_Pedidos_Pendientes ON dbo.Pedidos (Fecha) INCLUDE (ClienteId, Total) WHERE Estado = 3;
      ÍndiceFilasPáginas
      IX_Pedidos_Fecha (Fecha) INCLUDE (Total), completo400.0001.250
      IX_Pedidos_Pendientes, filtrado por Estado = 33.98922

      Cincuenta y siete veces más chico, más barato de mantener (una inserción con estado 1 ni lo toca) y con estadísticas propias sobre la porción que importa. Ahora la trampa:

      ConsultaLecturasPlan
      WHERE Estado = 3 AND Fecha >= '2026-06-01' (literales)5Index Seek sobre el filtrado
      WHERE Estado = @e AND Fecha >= @f con @e = 3 (sp_executesql)10.544Clustered Index Scan, con el aviso UnmatchedIndexes
      WHERE Estado = 3 AND Fecha >= @f (solo la fecha parametrizada)5Index Seek sobre el filtrado

      Con Estado como parámetro, el índice filtrado no se usa. El plan se compila una vez y se reutiliza con cualquier valor de @e; como el índice solo tiene el estado 3, un plan que lo use sería incorrecto para @e = 1, y el optimizador lo descarta. Lo avisa en el plan con UnmatchedIndexes. Desde Dapper o EF Core, donde todo lo que viene de una variable de C# se parametriza, esto pasa sin que nadie lo note.

      Los arreglos: escribir la condición del filtro como literal en el SQL (en EF, .Where(p => p.Estado == 3) con la constante en el código, no en una variable; o una consulta distinta para pendientes); OPTION (RECOMPILE), que compila con el valor real cada vez; o en un procedimiento, IF @e = 3 con la consulta literal adentro.

      Qué me llevo

      • Índice filtrado para el subconjunto chico que se consulta siempre: pendientes, activos, no borrados.
      • La columna del filtro tiene que aparecer como literal en la consulta, o el índice no se usa. Buscá «UnmatchedIndexes» en el plan.

      Capítulo 10Estadísticas, variables y parámetros

      El optimizador no mira los datos: mira un resumen de los datos, las estadísticas, y con eso decide. Para IX_Pedidos_ClienteId, DBCC SHOW_STATISTICS muestra un histograma de hasta 200 escalones; estos son los primeros:

      RANGE_HI_KEYEQ_ROWSRANGE_ROWSAVG_RANGE_ROWSSe lee como
      1100.00001El cliente 1 tiene exactamente 100.000 pedidos
      138147985,87Entre el 2 y el 137 hay 798 pedidos, unos 5,9 por cliente; el 138 tiene 14
      430141.7566,03Entre el 139 y el 429, unos 6 por cliente
      … y así hasta el cliente 50.000. Densidad general: 0,00002 (1 / 49.870 valores distintos), o sea 8 filas por cliente «promedio».

      Con eso, el optimizador estima y elige. El punto es con qué valor estima, y eso depende de cómo se escribe la consulta:

      ConsultaEstimóHuboLecturasTiempoPlan
      WHERE ClienteId = 1 (literal)100.000100.00010.54461 msClustered Index Scan (correcto: 100.000 lookups serían peor)
      WHERE ClienteId = 4242 (literal)65190 msIndex Seek + Key Lookup ×5
      DECLARE @c int = 1; … WHERE ClienteId = @c8100.000300.177225 msIndex Seek + Key Lookup ×100.000
      DECLARE @c int = 4242; … WHERE ClienteId = @c85190 msIndex Seek + Key Lookup ×5
      Lo mismo con @c = 1 y OPTION (RECOMPILE)100.000100.00010.54466 msClustered Index Scan

      La tercera fila es la que duele. Con una variable local, el optimizador no conoce el valor al compilar (el DECLARE y el SELECT se compilan juntos, antes de ejecutarse) y usa la densidad: 8 filas. Para 8 filas, seek más lookup es perfecto. Para 100.000, son 300.177 lecturas: 28 veces más que el plan correcto. OPTION (RECOMPILE) lo arregla porque compila con el valor ya asignado.

      Con parámetros (un procedimiento almacenado, o sp_executesql, que es lo que mandan Dapper y EF Core) pasa otra cosa: el optimizador sí ve el valor de la primera ejecución y compila el plan para ese valor; el plan queda en caché y las siguientes ejecuciones lo reutilizan con cualquier valor. Si la primera fue el cliente 4242, el mayorista hereda el plan de 5 filas. Es el parameter sniffing, y es la misma tabla de arriba vista desde la caché. En Plan en criollo, el ejemplo «Parameter sniffing con spill» es exactamente eso.

      Los remedios, de menos a más invasivo: OPTION (RECOMPILE) en la consulta puntual (cuesta una compilación por ejecución; para una consulta que corre diez veces por segundo con 2 ms de compilación, es aceptable; para mil, no); OPTION (OPTIMIZE FOR (@c = valor típico)) o OPTIMIZE FOR UNKNOWN; separar la consulta en dos cuando hay un caso claramente distinto; o un índice cubriente, que hace que el mismo plan sirva para los dos (capítulo 5: 375 lecturas para 100.000 filas y 3 para 5). SQL Server 2022 suma la optimización de planes sensibles a parámetros, que guarda hasta tres planes por consulta según el rango del valor.

      Y lo básico: las estadísticas se actualizan solas cuando cambia un 20 % de la tabla (menos en tablas grandes, desde 2016), y a mano con UPDATE STATISTICS tabla WITH FULLSCAN. Si el plan estima 1 fila donde hay 100.000 y no hay variables ni parámetros de por medio, lo primero es eso.

      Qué me llevo

      • Literal: estima exacto. Variable local: estima el promedio. Parámetro: estima con el primer valor y reutiliza.
      • Una consulta que a veces vuela y a veces se arrastra, con el mismo texto: parameter sniffing. Compará el valor compilado con el ejecutado en el plan.
      • El índice cubriente es el remedio que no tiene efectos secundarios.

      Capítulo 11El costo de escribir

      Cada índice es una copia parcial de la tabla que hay que mantener en cada INSERT, en cada DELETE y en cada UPDATE que toque sus columnas. Insertamos 100.000 pedidos en una tabla vacía con solo la clave primaria, y después en la misma tabla con cinco índices no agrupados (sobre ClienteId, Fecha, Estado, Total y (Estado, Fecha) INCLUDE (ClienteId, Total)):

      OperaciónLecturasTiempoPlan
      INSERT de 100.000 filas, solo clave primaria15.123214 msClustered Index Insert
      INSERT de 100.000 filas, con 5 índices más234.9911.806 msClustered Index Insert + 5 × (Table Spool → Sort → Index Insert)
      UPDATE Estado en 10.000 filas (columna con 2 índices)254123 msClustered Index Update + mantenimiento de IX3 e IX5
      UPDATE Observaciones en 10.000 filas (sin índices)25521 msClustered Index Update

      Ocho veces y media más lento con cinco índices: por cada uno, el motor ordena las 100.000 filas nuevas según su clave y las inserta. El UPDATE lo muestra desde el otro lado: cambiar una columna indexada cuesta seis veces más que cambiar una que no lo está, con la misma cantidad de filas. En espacio, los cinco índices suman 1.189 páginas sobre las 2.511 de la tabla: un 47 % más.

      Esto no es un argumento contra los índices: la tabla de ejemplo sin índices es la que lee 10.000 páginas para encontrar 5 filas. Es un argumento contra los índices que nadie usa, y contra crear uno por cada consulta sin mirar si uno existente ya la cubre con una columna más. Capítulo 13.

      Qué me llevo

      • Cada índice se paga en cada escritura. Cinco índices, 8× más lento el INSERT masivo.
      • Actualizar una columna indexada cuesta mucho más que una que no lo está: ojo con indexar columnas que cambian seguido (UltimaModificacion, contadores).
      • Para cargas masivas: cargar primero, indexar después.

      Capítulo 12Columnstore: otro animal

      Todo lo anterior son índices «de filas»: cada página guarda filas completas. Un índice columnstore guarda cada columna por separado, comprimida, en segmentos de un millón de filas, y el motor procesa de a lotes (batch mode). Está pensado para sumar y agrupar millones de filas, no para buscar una. Sobre Items (1,2 millones):

      CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Items ON dbo.Items (PedidoId, ProductoId, Cantidad, PrecioUnitario);

SELECT pr.Categoria, COUNT_BIG(*), SUM(i.Cantidad * i.PrecioUnitario)
FROM dbo.Items i JOIN dbo.Productos pr ON pr.ProductoId = i.ProductoId
GROUP BY pr.Categoria;
      SituaciónLecturasTiempoPlan
      Agregación con índices de filas5.31953 msIndex Scan de 1,2 M filas, 3 Hash Match, paralelo con 4 hilos
      Agregación con el columnstore17 (más lecturas de segmentos, que no se cuentan acá)22 msColumnstore Index Scan en batch mode, serial
      Búsqueda puntual: WHERE PedidoId = 12345630 msIndex Seek sobre el índice de filas de siempre
      Índice sobre ItemsPáginas
      Agrupado (la tabla)5.662
      IX_Items_PedidoId, de filas, con las mismas 4 columnas5.219
      NCCI_Items, columnstore, con las mismas 4 columnas1.256

      Con 1,2 millones de filas la diferencia es 2,4× en tiempo y 4× en espacio, y el columnstore lo hizo con un hilo contra cuatro. El experimento es chico a propósito; con decenas de millones de filas la diferencia es de uno o dos órdenes de magnitud, porque la compresión por columna y el batch mode escalan con el volumen. La búsqueda puntual siguió usando el índice de filas: el optimizador elige por consulta, y por eso un columnstore no agrupado convive con los índices normales. Es la forma de tener reportes sobre la misma base transaccional sin armar un data warehouse.

      Lo que no se midió acá: el costo de mantenerlo con muchas inserciones chicas (van a un «deltastore» de filas hasta juntar un millón) y los UPDATE, que en columnstore son un DELETE más un INSERT. Para tablas que se escriben de a una fila todo el día y se consultan por clave, no es la herramienta.

      Qué me llevo

      • Agregaciones sobre millones de filas: columnstore no agrupado sobre las columnas del reporte.
      • Convive con los índices de filas; cada consulta usa el que le conviene.
      • No es para buscar una fila ni para tablas con muchas actualizaciones.

      Capítulo 13Lo que el servidor sabe de tus índices

      Después de todos los experimentos le preguntamos al servidor qué registró. Dos vistas, las dos acumuladas desde el último reinicio (o desde que se creó el índice):

      SELECT i.name, u.user_seeks, u.user_scans, u.user_lookups, u.user_updates
FROM sys.indexes i
LEFT JOIN sys.dm_db_index_usage_stats u ON u.object_id = i.object_id AND u.index_id = i.index_id AND u.database_id = DB_ID()
WHERE i.object_id = OBJECT_ID('dbo.Pedidos');
      ÍndiceSeeksScansLookupsUpdatesLectura
      PK_Pedidos1270772Se recorrió 70 veces y recibió 77 lookups: los capítulos 4, 5 y 10
      IX_Pedidos_ClienteId48400Se usa para buscar. Vale lo que cuesta

      Un índice con user_updates altos y seeks, scans y lookups en cero durante semanas es un índice que solo cuesta. Antes de borrarlo, dos precauciones: que el servidor lleve bastante tiempo encendido (los contadores se pierden al reiniciar) y que no sea un índice único, que además de buscar está garantizando algo.

      La otra vista es la de índices faltantes: cada vez que el optimizador arma un plan y piensa «con un índice acá sería más barato», lo anota. Es lo que SSMS muestra en verde arriba del plan.

      SELECT d.statement, d.equality_columns, d.inequality_columns, d.included_columns,
       s.user_seeks, s.avg_user_impact, s.avg_total_user_cost
FROM sys.dm_db_missing_index_details d
JOIN sys.dm_db_missing_index_groups g ON g.index_handle = d.index_handle
JOIN sys.dm_db_missing_index_group_stats s ON s.group_handle = g.index_group_handle
WHERE d.database_id = DB_ID()
ORDER BY s.avg_user_impact * s.avg_total_user_cost * s.user_seeks DESC;

      En la base de prueba, al final quedó una sola sugerencia: Clientes por FechaAlta con Nombre incluida, impacto 54 %, pedida una vez. Las de Pedidos se borraron solas cuando se crearon y eliminaron los índices de los capítulos (la vista se limpia cuando cambia el esquema de la tabla). Cómo leerla: el impacto es cuánto bajaría el costo de esa consulta; user_seeks es cuántas veces se pidió; el costo, cuánto pesa la consulta. Un impacto de 95 % en una consulta que corrió una vez no vale un índice; uno de 40 % en una que corre diez mil veces por hora, sí. Y siempre hay que cruzarla con los índices que existen: muchas veces la sugerencia es un índice existente más una columna en INCLUDE, y lo correcto es modificar ese, no crear otro.

      Qué me llevo

      • sys.dm_db_index_usage_stats para encontrar índices que solo cuestan.
      • sys.dm_db_missing_index_details para encontrar los que faltan, ponderando por cuántas veces se pidieron.
      • Las sugerencias son por consulta: hay que consolidarlas contra lo que ya existe antes de crear nada.

      Para el código .NET

      • Proyectá columnas: .Select(p => new { … }) en EF, listas de columnas en Dapper. El índice cubriente depende de eso.
      • Tipos: varchar en la base, varchar en el parámetro. En EF Core, IsUnicode(false) o HasColumnType en la configuración de la entidad.
      • Fechas por rango: p.Fecha >= desde && p.Fecha < hasta. Nunca p.Fecha.Year == 2026 ni p.Fecha.Date == hoy.
      • Paginación por clave en listas largas; Skip/Take solo para las primeras páginas.
      • Los índices van en las migraciones: HasIndex(p => new { p.Estado, p.Fecha }).IncludeProperties(p => new { p.ClienteId, p.Total }).HasFilter("[Estado] = 3").
      • Cuando una consulta importa, mirá su plan real: SET STATISTICS XML ON y lo pegás en Plan en criollo.

      Cómo se hizo

      SQL Server 2022 Developer (16.0.4305) en un contenedor Linux con 4 CPU, base Tienda creada con el script del pie de experimentos.sql. Cada consulta se ejecutó desde Node con SET STATISTICS XML ON, se tomó el plan real que devuelve el servidor y de ahí salieron las lecturas lógicas (sumadas sobre todos los operadores), el tiempo (QueryTimeStats) y la forma del plan. Los tamaños vienen de sys.dm_db_partition_stats y sys.dm_db_index_physical_stats. Todo está en resultados.json, tal cual salió. Las cifras de tiempo son de un servidor sin carga y con los datos en memoria: comparalas entre sí, no con tu producción.
