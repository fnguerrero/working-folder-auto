    LINQ con el cronómetro en la mano

    Las preguntas de LINQ que aparecen en un code review, medidas en .NET 8, 9 y 10: tiempo y memoria de cada variante, y la regla práctica que queda.

    .NET 8.0.34, 9.0.21 y 10.0.13 · Windows 11 x64, 16 procesadores lógicos, GC de estación · arnés propio con Stopwatch (no es BenchmarkDotNet) · todos los números salen de resultados.json y de las corridas crudas del proyecto benchmarks/.

    Índice

      Antes de empezarCómo leer las tablas

      Cada celda tiene la mediana (promedio de las medianas de dos corridas de 12 muestras cada una), abajo el rango entre la muestra más rápida y la más lenta, y en color lo que asigna una ejecución en el heap. Una línea gruesa separa grupos: solo se comparan filas del mismo grupo, que además devuelven el mismo resultado (el programa lo verifica antes de medir). El signo ≈ marca las celdas donde las dos corridas difirieron más de un 25 %: ahí creele al orden de magnitud y nada más.

      La misma fuente se compiló para net8.0, net9.0 y net10.0 con el SDK de .NET 10 (o sea, con C# 14 en .NET 10 y la versión de lenguaje que corresponde a cada uno en los otros).

      Ojo: es una máquina de escritorio con otros procesos andando, sin aislar núcleos. Sirve para comparar órdenes de magnitud. Además, el JIT optimiza según lo que ve en la ejecución y según los datos: con otros datos (más o menos predecibles) varias filas cambian. No es BenchmarkDotNet.

      Unidades: 1 µs son 1.000 ns, 1 ms son 1.000.000 ns.

      Capítulo 1Where y Select contra un for

      static long Linq(int[] a) => a.Where(x => x % 2 == 0).Select(x => x * 3).Sum();
static long Linq(List<int> l) => l.Where(x => x % 2 == 0).Select(x => x * 3).Sum();
static long For(int[] a)
{
    int s = 0;
    for (int i = 0; i < a.Length; i++) { int x = a[i]; if (x % 2 == 0) s += x * 3; }
    return s;
}
static long For(List<int> l)
{
    int s = 0;
    for (int i = 0; i < l.Count; i++) { int x = l[i]; if (x % 2 == 0) s += x * 3; }
    return s;
}
static long Foreach(List<int> l)
{
    int s = 0;
    foreach (var x in l) if (x % 2 == 0) s += x * 3;
    return s;
}

      El for gana siempre, entre 1,5 y 8 veces según el tamaño, la colección y la versión. La cadena de LINQ asigna una cantidad fija y chica (los iteradores: 104 bytes sobre array, 152 sobre List), no crece con los elementos. Lo que crece es el tiempo por elemento. Y no todo mejora al actualizar: sobre una List de 10.000, esta cadena midió más lenta en .NET 9 y 10 que en .NET 8.

      Qué me llevo

      • En una pantalla o un endpoint con cientos de elementos, la diferencia son décimas de microsegundo: escribí lo que se lea mejor.
      • En un bucle caliente, medilo y, si pesa, escribí el for.

      Sobre una secuencia perezosa, Any() frena en el primer elemento y Count() > 0 la recorre entera: cientos de veces de diferencia con 10.000 elementos. Con condición pasa lo mismo (el elemento buscado está al principio). Sobre una List directa las tres formas cuestan nanosegundos, porque la cantidad ya se sabe.

      Qué me llevo

      • Para preguntar si hay alguno, Any. Nunca está mal.
      • Si el tipo es List o array, Count / Length como propiedad es igual de bueno.

      Acá la regla de memoria se complica. En memoria es clara: materializar cuesta de 20 a 150 KB por ejecución donde la cadena directa asigna menos de 200 bytes. En tiempo, para foreach el ToList() fue bastante más lento. Pero en la cadena con Sum() pasó al revés: con ToList() en cada paso las medianas fueron más bajas en .NET 8 y 9, y en .NET 10 las dos corridas no coincidieron. Una explicación posible (no verificada): recorrer y sumar una lista ya armada tiene caminos más rápidos que atravesar tres iteradores.

      Qué me llevo

      • Un ToList() que se recorre una sola vez es basura para el GC: sacalo.
      • Contra una base de datos es otra discusión (trae filas de más); acá todo es en memoria.

      La respuesta depende de la versión. En .NET 8, First sobre un array fue unas 10 veces más lento que el for y List.Find le ganaba a First. En .NET 9 y 10, First sobre List pasó a estar entre lo más rápido; sobre array mejoró mucho pero siguió varias veces atrás del for y de Array.Find.

      Qué me llevo

      • Cambiar First por Find «por rendimiento» era razonable en .NET 8; en 9 y 10, sobre una lista, ya no.
      • Todas son búsquedas lineales. Si se repite, la mejora está en el capítulo 8.

      Capítulo 6Enumerar varias veces

      // "Caro" hace algo de trabajo por elemento: simula una proyección con cálculo.
static int Caro(Prod p) { int h = p.Precio; for (int i = 0; i < 20; i++) h = unchecked(h * 31 + i); return h & 1023; }
static IEnumerable<int> Puntajes() => Prods.Select(Caro);

static long TresRecorridas() { var q = Puntajes(); return q.Count() + (long)q.Sum() + q.Max(); }
static long Materializada() { var q = Puntajes().ToList(); return q.Count + (long)q.Sum() + q.Max(); }
static long UnForeach()
{
    int n = 0, s = 0, max = int.MinValue;
    foreach (var x in Puntajes()) { n++; s += x; if (x > max) max = x; }
    return n + (long)s + max;
}

      Un IEnumerable armado con Select no guarda nada: cada Count(), Sum() o Max() vuelve a ejecutar la proyección. Contado aparte: con 10.000 elementos se ejecutó 30.000 veces en las tres recorridas y 10.000 materializando una vez. En tiempo, más de 3 veces. Materializar costó 40 KB.

      Qué me llevo

      • Si vas a consumir una secuencia dos veces, materializala (o juntá todo en un recorrido).
      • Si detrás hay una consulta a la base o un archivo, cada recorrida lo repite.

      • Un First o un List.Contains adentro de un foreach es un bucle doble escondido.
