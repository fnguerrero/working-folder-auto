    Async con el cronómetro en la mano

    Ocho preguntas sobre async/await en .NET, cada una con el código de las variantes, lo que tardaron, lo que asignaron y la regla que queda. Para discutir un code review con números en vez de con reglas de memoria.

    .NET 8.0.34 y .NET 10.0.13 · Windows 11 x64, 16 procesadores lógicos, GC de estación · arnés propio con Stopwatch (no es BenchmarkDotNet) · todos los números salen de resultados.json y de las corridas crudas del proyecto benchmarks/.

    Índice

      Antes de empezarCómo se midió y cuánto creerle

      No había BenchmarkDotNet disponible, así que el arnés es propio: calibra cuántas operaciones entran en una muestra de unos 30 ms, calienta en tres tandas con pausas para que el JIT por niveles termine, y toma 12 muestras. Las mediciones de tiempo y memoria se corrieron dos veces en cada runtime (el thread pool del capítulo 4, una). En las tablas, el número grande es la mediana (el promedio de las dos medianas) y abajo va el rango entre la muestra más rápida y la más lenta. Los bytes salen de GC.GetAllocatedBytesForCurrentThread cuando todo pasa en un hilo, y de GC.GetTotalAllocatedBytes cuando la operación salta entre hilos (ahí puede colarse algún byte de otro lado).

      Ojo: es una máquina de escritorio con otros procesos andando, sin aislar núcleos ni fijar la frecuencia. Los números sirven para comparar órdenes de magnitud y variantes entre sí. Una diferencia del 10 % o menos entre dos filas, acá, es empate.

      Unidades: 1 µs son 1.000 ns, 1 ms son 1.000.000 ns.

      Capítulo 1¿Cuánto cuesta un await?

      Depende de una sola cosa: si lo que se espera ya terminó o no. Si terminó, el método sigue de largo en el mismo hilo. Si no, hay que guardar el estado, devolver el hilo y retomar después.

      [MethodImpl(MethodImplOptions.NoInlining)]
static int Sincrono() => _valor;

static async Task<int> AsyncSinEsperar() { await Task.CompletedTask; return _valor; }
static async Task<int> AsyncAwaitTareaLista() => await TareaGuardada;
static async Task<int> AsyncConYield() { await Task.Yield(); return _valor; }
static async Task<int> AsyncConDelay() { await Task.Delay(1); return _valor; }

      Un async que completa sincrónicamente cuesta unos 10 a 20 ns y asigna 72 bytes (la Task<int> del resultado). Suspender de verdad con Task.Yield() sube a unos 400 ns y 96 bytes: unas 30 veces más, y aun así menos de medio microsegundo. La última fila es otra historia: Task.Delay(1) tardó alrededor de 15 ms, porque en esta máquina con Windows el timer no despertó antes de eso.

      Qué me llevo

      • Frente a una consulta de 1 ms, el costo del await no se ve: es miles de veces menor.
      • En un bucle de millones de llamadas que casi siempre completan solas, sí suma.
      • No uses Task.Delay(1) creyendo que esperás 1 ms.

      Capítulo 2¿ValueTask es más rápido?

      El caso para el que existe: un método que casi siempre tiene el valor en caché. Se midió con 100 %, 90 % y 0 % de aciertos.

      // Un método que casi siempre tiene el valor en caché.
// "cada" = 1 de cada cuántas llamadas tiene que ir a buscarlo (0 = nunca).
static bool EnCache(int cada) => cada == 0 || ++_contador % cada != 0;

static async Task<int> LeerTask(int cada)
{
    if (EnCache(cada)) return _valor;
    await Task.Yield(); return _valor;
}

static async ValueTask<int> LeerValueTask(int cada)
{
    if (EnCache(cada)) return _valor;
    await Task.Yield(); return _valor;
}

// Sin "async" en el camino rápido: devuelve siempre la misma Task ya terminada.
static Task<int> LeerTaskGuardada(int cada) => EnCache(cada) ? TareaGuardada : Buscar();
static async Task<int> Buscar() { await Task.Yield(); return _valor; }

[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))]
static async ValueTask<int> LeerValueTaskConPool(int cada)
{
    if (EnCache(cada)) return _valor;
    await Task.Yield(); return _valor;
}

      Con todo en caché, async ValueTask evita los 72 bytes y fue más rápido que async Task. Pero la fila que gana es la menos glamorosa: devolver una Task guardada, sin async, tarda menos de 2 ns y no asigna. Eso sirve cuando el valor cacheado es siempre el mismo objeto. Con 90 % de aciertos las cuatro variantes quedan cerca en tiempo (alrededor de 40 a 50 ns), porque el 10 % que espera domina; las asignaciones sí cambian. Con 0 %, ValueTask asigna más que Task (104 contra 96 bytes) y no es más rápido.

      El builder con pool (PoolingAsyncValueTaskMethodBuilder) dejó las asignaciones en cero en los tres casos, pero no mejoró el tiempo, y en .NET 10 con 0 % de aciertos salió más lento. Exige además respetar al pie las reglas de ValueTask (un solo await), porque el objeto se reusa.

      Qué me llevo

      • ValueTask ahorra una asignación en el camino sincrónico. Si el método casi siempre espera, no ahorra nada.
      • Antes de cambiar la firma, probá devolver una Task ya creada.
      • El pool es una herramienta para cuando un profiler ya señaló esas asignaciones.

      Capítulo 3¿Cuánto pesa ConfigureAwait(false)?

      Una «biblioteca» hace diez esperas reales. Se llama desde un lugar sin SynchronizationContext (como un controlador de ASP.NET Core) y desde un contexto de un solo hilo con cola propia, armado a mano para imitar el de una aplicación de escritorio. No es WinForms ni WPF: un message loop real cuesta distinto.

      // "Biblioteca": diez esperas reales seguidas. El que la llama espera una sola vez.
static async Task<int> DiezEsperas(bool seguirContexto)
{
    int t = 0;
    for (int i = 0; i < 10; i++)
        t += await Task.Run(static () => 1).ConfigureAwait(seguirContexto);
    return t;
}

      Sin contexto (como ASP.NET Core) · ConfigureAwait(true)3,8 µs3,6 µs a 4,1 µs832 B3,8 µs3,7 µs a 3,9 µs832 B
      Contexto de un hilo (como la UI) · ConfigureAwait(true)8,0 µs7,3 µs a 8,6 µs1,4 KB7,6 µs6,8 µs a 8,1 µs1,4 KB
      Sin contexto (como ASP.NET Core) · ConfigureAwait(false)3,7 µs3,6 µs a 4,4 µs832 B3,8 µs3,7 µs a 4,2 µs832 B
      Contexto de un hilo (como la UI) · ConfigureAwait(false)4,1 µs4,0 µs a 4,4 µs880 B4,1 µs3,9 µs a 5,8 µs880 B

      Sin contexto, true y false dan lo mismo en tiempo y en bytes: no hay nada que capturar. Con contexto, true manda cada continuación de vuelta al hilo de la UI (10 Post por llamada contra 1, el del que llama) y tarda cerca del doble. Son unos 400 ns por espera: poco en tiempo, pero cada uno ocupa el hilo que dibuja la pantalla.

      Lo importante es otra cosa. Si alguien bloquea ese hilo con .Wait() o .Result:

      static async Task<int> Pide(bool seguirContexto)
{
    await Task.Delay(50).ConfigureAwait(seguirContexto);
    return 1;
}

// En el hilo del contexto, bloquea con .Wait() esperando un método async. ¿Termina?
static bool TerminaBloqueando(bool seguirContexto)
{
    var ui = new ContextoDeUnHilo();        // un hilo descartable: puede quedar trabado para siempre
    var fin = new ManualResetEventSlim();
    ui.Post(_ => { Pide(seguirContexto).Wait(); fin.Set(); }, null);
    return fin.Wait(2000);
}

      Con ConfigureAwait(true) el programa no terminó (se esperó 2 segundos): la continuación quiere volver a un hilo que está esperando justamente esa continuación. Con false terminó. Pasó igual en .NET 8 y .NET 10.

      Qué me llevo

      • En código de aplicación de ASP.NET Core, agregar ConfigureAwait(false) no cambió nada medible.
      • En una biblioteca que puede usarse desde una UI, sí corresponde.
      • false esquiva este deadlock, pero el problema de fondo es bloquear: hay que esperar con await.

      Capítulo 4La API que se traba: sync-over-async

      Entran pedidos al thread pool a un ritmo fijo durante 10 segundos (llegan igual aunque el servidor esté atrasado). Cada uno espera 100 ms de «base de datos». Además, cada 250 ms entra un «health check» que no hace nada: lo que tarda en contestar es lo que espera cualquier pedido en la cola. No hay HTTP ni Kestrel: es el thread pool solo, un proceso nuevo por escenario, una corrida de cada uno.

      // Espera sin ocupar un hilo.
static async Task PedidoAsync() => await Task.Delay(EsperaMs);

// Sync-over-async: una operación async a la que alguien le pone .Result.
static async Task<int> Consulta() { await Task.Delay(EsperaMs); return 1; }
static int PedidoResult() => Consulta().Result;

// Bloqueo "a secas", sin Task de por medio.
static void PedidoSleep() => Thread.Sleep(EsperaMs);

      Con await, de 100 a 800 pedidos por segundo salen todos en unos 109 ms, con menos de 20 hilos. Con .Result anda igual de bien hasta 200 por segundo, y ahí está la trampa: en las pruebas con poca carga no se nota. A 400 se derrumba: salen alrededor de 140 por segundo, el p99 pasa los 40 segundos, el «health check» que no hace nada tarda decenas de segundos y el pool llega a 132 hilos a los 10 segundos. A 800, miles de pedidos seguían sin contestar 45 segundos después de cortar la carga.

      ¿Por qué 132 hilos no alcanzan, si en teoría harían falta unos 40 para 400 pedidos de 100 ms? La explicación que cierra con lo medido (no se instrumentó el runtime para demostrarlo): cada espera que termina necesita un hilo libre para completar la Task que alguien está bloqueado esperando, y ese trabajo hace cola detrás de los pedidos nuevos, que a su vez se bloquean.

      Thread.Sleep salió peor que .Result a 200 por segundo: se quedó en unos 20 hilos. El pool desde .NET 6 se entera cuando un hilo suyo se bloquea esperando una Task y agrega hilos más rápido; con Sleep esa ayuda no aparece. Subir el mínimo a 200 hilos salvó todos los escenarios medidos, pero es un parche: con esperas más largas o más carga el techo vuelve a aparecer, y acá no se midió.

      Qué me llevo

      • API que «se traba cada tanto» con la CPU baja: buscá .Result, .Wait() y GetAwaiter().GetResult().
      • Mirá el contador threadpool-queue-length y cuántos hilos tiene el pool (dotnet-counters).
      • ThreadPool.SetMinThreads compra tiempo mientras se arregla el código. El arreglo es await de punta a punta.

      En tiempo y memoria, cuando completa sin esperar, son iguales. La diferencia no es de rendimiento. Se lanzó un proceso aparte para cada caso, con la excepción después de una espera y un try/catch alrededor de la llamada:

      static async void ExplotaVoid() { await Task.Delay(50); throw new InvalidOperationException("boom"); }

      Qué me llevo

      • async void solo para manejadores de eventos, con try/catch adentro.
      • Una Task sin await no tira el proceso, pero se traga el error: tampoco sirve para «disparar y olvidar».

      Capítulo 6Task.Run adentro de una API

      [MethodImpl(MethodImplOptions.NoInlining)]
static int Trabajo(int vueltas)
{
    int h = _valor;
    for (int i = 0; i < vueltas; i++) h = unchecked(h * 31 + i);
    return h;
}
static Task<int> Directo(int vueltas) => Task.FromResult(Trabajo(vueltas));
static async Task<int> ConTaskRun(int vueltas) => await Task.Run(() => Trabajo(vueltas));

      await Task.Run agrega unos 450 ns y 180 bytes: el pasaje a otro hilo del mismo pool que ya estaba atendiendo el pedido. Con un trabajo chico eso lo hace unas 45 veces más caro; con uno de varios microsegundos queda en alrededor de un 7 %. En ninguno de los dos casos gana nada: el que llama espera igual.

      Qué me llevo

      • En un controlador, envolver trabajo en Task.Run para que «sea async» no libera capacidad: ocupa otro hilo.
      • Tiene sentido en una UI (sacar trabajo del hilo que dibuja) o para paralelizar a propósito, midiendo.

      Capítulo 7IAsyncEnumerable contra la lista entera

      public sealed record Fila(int Id, int Monto);

static async Task<List<Fila>> TraerLista(int total, int pagina)
{
    var lista = new List<Fila>();
    for (int i = 0; i < total; i++)
    {
        if (pagina > 0 && i % pagina == 0) await Task.Yield();   // "llegó otra página"
        lista.Add(new Fila(i, i % 100));
    }
    return lista;
}

static async IAsyncEnumerable<Fila> Recorrer(int total, int pagina)
{
    for (int i = 0; i < total; i++)
    {
        if (pagina > 0 && i % pagina == 0) await Task.Yield();
        yield return new Fila(i, i % 100);
    }
}

      Qué me llevo

      • Para resultados grandes que se procesan de a uno, el stream baja la memoria y adelanta la primera respuesta.
      • Mientras dura, la fuente (conexión, reader) sigue abierta: un consumidor lento la retiene.
      • Si vas a recorrer dos veces o necesitás la cantidad, pedí la lista.

      Capítulo 8ValueTask mal usado y las asignaciones

      static ValueTask<int> Listo() => new(_valor);

      await de un ValueTask, como corresponde1,7 ns1,7 ns a 1,8 ns0 B1,7 ns1,6 ns a 1,9 ns0 B

      Un ValueTask que ya tiene el resultado no cuesta casi nada. Cada vez que se lo convierte en otra cosa, aparece la asignación que se quería evitar: .AsTask() crea la Task (72 bytes), pasarlo como object lo encajona (32 bytes) y juntarlos en un WhenAll suma varios cientos. Esperar dos guardados en orden no asigna.

      Ojo: esperar dos veces el mismo ValueTask, o leer .Result antes de que termine, es uso inválido. Con un resultado inmediato puede parecer que anda; con uno respaldado por un objeto reusado (como el builder con pool) el comportamiento no está definido. No se midió porque no hay un resultado correcto que medir.

      La máquina de estados en sí se ve en los capítulos 1 y 2: sin suspender, un método async ValueTask no asigna; al suspender, el estado pasa al heap (los 96 a 104 bytes de las filas que esperan).

      Qué me llevo

      • Un ValueTask se espera una vez, enseguida, y no se guarda.
      • Si el código lo termina pasando a WhenAll con .AsTask(), probablemente convenía devolver Task.
