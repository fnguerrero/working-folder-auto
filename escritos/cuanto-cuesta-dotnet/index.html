    Cuánto cuesta cada cosa en .NET 8

    129 microbenchmarks sobre las discusiones de todos los días en un equipo .NET (¿StringBuilder o concatenar? ¿LINQ o bucle? ¿cuánto cuesta una excepción, un async de más, una regex, el logging que no se ve?), medidos con BenchmarkDotNet y no de oído. Con el código de cada uno, el número, y qué hacer con eso.

    .NET 8.0.32 · BenchmarkDotNet 0.14 · Linux x64, contenedor con 2 vCPU · Release, TieredPGO, workstation GC · todos los números salen de resultados.json, generado por el proyecto de benchmarks/. Las tablas se generan desde el JSON, no se tipean.

    Índice

      Antes de empezarCómo leer estos números (y cómo no)

      Cada vez que en una revisión de código alguien dice «eso es lento» o «eso asigna memoria», vale la pena preguntar: ¿cuánto? Casi nunca hay un número en la mesa. Este escrito es ese número, para las discusiones más frecuentes, medido en un .NET 8 real con BenchmarkDotNet, la herramienta que usa el propio equipo de .NET.

      Cómo se midió: cada benchmark es un método con [Benchmark] en un proyecto Release. BenchmarkDotNet lo corre miles de veces por iteración, descuenta el costo del bucle, hace 3 iteraciones de calentamiento (así el JIT ya hizo su trabajo, incluido el tiered PGO) y 5 de medición, e informa la media por operación y, con MemoryDiagnoser, los bytes asignados por operación en el heap. Cada capítulo tiene un benchmark base y los demás se comparan contra él.

      Las tres reglas para no sacar conclusiones equivocadas

      1. Los valores absolutos son de esta máquina: un contenedor con 2 vCPU en una nube compartida. En tu notebook van a ser otros, probablemente más bajos. Lo que viaja de una máquina a otra es la relación entre variantes (3× más lento, 10× menos memoria), no el nanosegundo.
      2. Un nanosegundo es un nanosegundo. Si algo tarda 60 ns en vez de 330 ns es 5× más lento, cierto, y también es cierto que en un endpoint que tarda 20 ms y lo llama una vez, da exactamente igual. Mirá la escala: ns es despreciable salvo en un bucle caliente; µs empieza a pesar si se repite por fila o por pedido; ms ya se ve en el p99. Las tablas tienen la unidad al lado del número a propósito.
      3. La memoria importa tanto como el tiempo, o más. Lo que se asigna, el GC lo tiene que recolectar. En una API con miles de pedidos por segundo, 10 KB de basura por pedido son decenas de MB por segundo de trabajo para el GC, pausas de Gen0 y, si sobrevive algo, Gen1 y Gen2. Un benchmark con «0 B» no genera trabajo para el GC; uno con 2 KB sí. Muchas de las mejoras que siguen son de memoria más que de tiempo.
      Qué no es esto. No es «hacé siempre lo rápido». Casi todo lo que aparece como lento es perfectamente legible y correcto, y en el 95 % del código da igual. El valor de los números es saber dónde está el otro 5 %: el bucle que procesa 100.000 filas, el middleware que corre en cada pedido, el serializador, el logging. Ahí, y solo ahí, elegir la variante barata se nota.

      Capítulo 1Armar texto: concatenar, StringBuilder, interpolar

      La discusión más vieja de todas. Veinte pedazos de texto para unir con comas, y una línea de log típica con cuatro valores.

      // Veinte partes
[Benchmark(Baseline = true)] public string ConcatEnBucle() { var s = ""; foreach (var p in _partes) s += p + ","; return s; }
[Benchmark] public string StringBuilder_() { var sb = new StringBuilder(); foreach (var p in _partes) { sb.Append(p); sb.Append(','); } return sb.ToString(); }
[Benchmark] public string StringJoin() => string.Join(",", _partes) + ",";

// Cuatro valores (int, string, decimal, DateTime)
[Benchmark] public string Interpolacion() => $"Pedido {_id} de {_nombre}: {_total} el {_fecha:yyyy-MM-dd}";
[Benchmark] public string StringFormat() => string.Format("Pedido {0} de {1}: {2} el {3:yyyy-MM-dd}", _id, _nombre, _total, _fecha);
[Benchmark] public string ConcatOperador() => "Pedido " + _id + " de " + _nombre + ": " + _total + " el " + _fecha.ToString("yyyy-MM-dd");

      Concatenar con += en un bucle crea una cadena nueva en cada vuelta (veinte cadenas intermedias que van a la basura: 3,5 KB para 20 partes). StringBuilder asigna menos pero no es gratis: su buffer interno también crece y se copia. El ganador es el que menos gente usa: string.Join calcula el largo total primero y escribe una sola vez. Lo mismo vale para string.Concat(IEnumerable).

      Para armar una línea con pocos valores, la interpolación gana por mucho y no es casualidad: desde C# 10 $"..." se compila a un DefaultInterpolatedStringHandler que formatea cada valor directo en un buffer alquilado, sin crear las cadenas intermedias que sí crea string.Format (que además tiene que parsear la plantilla cada vez) ni el + (que llama a ToString() de cada valor y después concatena). Mitad de tiempo, menos de la mitad de memoria.

      Qué me llevo

      • Para unir una colección: string.Join. Para unas pocas piezas conocidas: interpolación. StringBuilder para cuando armás texto de a poco y no sabés cuántas piezas son.
      • string.Format no tiene ya ninguna ventaja sobre $"", salvo que la plantilla venga de un recurso.
      • El += en un bucle es lo único que de verdad hay que evitar, y por la memoria más que por el tiempo.

      Capítulo 2Comparar texto: cultura, ordinal y el ToLower() de más

      Esto no es solo rendimiento, es corrección: "i".ToUpper() en turco no es "I", y StartsWith sin especificar comparación usa la cultura actual, que en algunos casos ignora caracteres. Pero acá medimos cuánto cuesta cada forma de preguntar «¿son iguales?» y «¿empieza con?» sobre 1.000 nombres de archivo.

      [Benchmark(Baseline = true)] public bool EqualsOrdinalIgnoreCase() => string.Equals(_a, _b, StringComparison.OrdinalIgnoreCase);
[Benchmark] public bool ToLowerEquals() => _a.ToLower() == _b.ToLower();
[Benchmark] public bool ToUpperInvariantEquals() => _a.ToUpperInvariant() == _b.ToUpperInvariant();
[Benchmark] public bool EqualsCulturaIgnoreCase() => string.Equals(_a, _b, StringComparison.CurrentCultureIgnoreCase);

[Benchmark] public int StartsWithOrdinal() { ... if (s.StartsWith("Archivo_00", StringComparison.Ordinal)) n++; ... }
[Benchmark] public int EndsWithDefault() { ... if (s.EndsWith(".pdf")) n++; ... }

      El patrón a.ToLower() == b.ToLower() crea dos cadenas nuevas para tirarlas enseguida y encima pasa por las reglas de la cultura actual: 5× más lento y 200 B de basura por comparación. StringComparison.OrdinalIgnoreCase compara carácter por carácter sin asignar nada y es lo que querés para identificadores, nombres de archivo, claves, headers, cualquier cosa que no sea texto para mostrarle a una persona.

      La trampa grande es StartsWith("...") y EndsWith("...") sin segundo parámetro: esas dos sobrecargas usan la cultura actual (a diferencia de Contains, IndexOf(char) y Equals, que son ordinales). Pasan por ICU y son entre 8 y 12 veces más lentas, además de dar resultados raros con guiones, apóstrofos o caracteres de control. El analizador CA1310 avisa justamente de esto.

      Qué me llevo

      • Nunca ToLower()/ToUpper() para comparar. StringComparison.OrdinalIgnoreCase.
      • StartsWith y EndsWith siempre con StringComparison.Ordinal (o el char directo: s.EndsWith('/')). Activá CA1310.
      • La comparación por cultura es para ordenar y comparar texto que ve el usuario. Nada más.

      Capítulo 3Partir texto: Split, Substring y Span

      Una línea de un archivo plano con siete campos separados por punto y coma, de la que hay que sacar tres números. Después, lo mismo mil veces (un archivo chico de mil líneas).

      // "4821;2026-10-16;1234.50;ARS;Nicolás;aprobado;3"
[Benchmark(Baseline = true)] public decimal SplitYParse()
{
    var c = _linea.Split(';');
    return int.Parse(c[0]) + decimal.Parse(c[2], CultureInfo.InvariantCulture) + int.Parse(c[6]);
}
[Benchmark] public decimal SpanYParse()
{
    ReadOnlySpan<char> s = _linea;
    int p1 = s.IndexOf(';'); int id = int.Parse(s[..p1]);
    s = s[(p1 + 1)..]; s = s[(s.IndexOf(';') + 1)..];
    int p3 = s.IndexOf(';'); decimal total = decimal.Parse(s[..p3], CultureInfo.InvariantCulture);
    int cant = int.Parse(s[(s.LastIndexOf(';') + 1)..]);
    return id + total + cant;
}

      SplitYParse base228,9 ns1,00×336 B
      SpanYParse106,4 ns2,2× más rápido0 B
      SplitMil237,1 µs1.036× más lento459,8 KB
      SpanMil100,3 µs438× más lento0 B

      Split crea un array y una cadena nueva por cada campo, aunque solo uses tres: 336 B por línea, 470 KB por el archivo de mil. La versión con ReadOnlySpan<char> no asigna nada (todas las APIs de parseo aceptan spans desde .NET Core 2.1: int.Parse, decimal.Parse, DateTime.ParseExact, Guid.Parse) y tarda menos de la mitad. Substring es lo mismo en chico: 48 B por llamada contra cero.

      El código con spans es más feo, no hay vuelta: eso es lo que se paga. Vale la pena en el parser de un formato (CSV, un log, un protocolo), en el middleware que lee headers, en lo que corre por cada fila. No vale la pena en el handler que parte una cadena una vez. Si te quedás con Split, al menos Split(';', 3) para no cortar lo que no vas a usar, o StringSplitOptions.TrimEntries en vez de un Trim() por campo.

      Qué me llevo

      • En un parser, AsSpan(), IndexOf y los Parse(ReadOnlySpan<char>): 0 B. En el resto del código, Split está perfecto.
      • Substring crea una cadena; AsSpan(inicio, largo) no. Si lo que sigue acepta span, usá span.
      • .NET 8 tiene MemoryExtensions.Split(span, Span<Range>, separador) para partir sin asignar; .NET 9 agrega el enumerador de Split sobre spans.

      Capítulo 4Listas y LINQ: cuánto cuesta la comodidad

      Mil enteros y mil pedidos (un record con id, cliente, total y estado). Las preguntas de siempre: ¿la capacidad inicial de la lista importa?, ¿foreach o for?, ¿LINQ o bucle?, ¿Any() o Count > 0?

      La capacidad inicial ahorra un 40 % del tiempo y la mitad de la memoria: sin ella, la lista arranca con 4 lugares y se duplica ocho veces hasta llegar a 1.024, copiando cada vez y dejando los arrays viejos para el GC. Si sabés cuántos elementos vienen (el Count de otra colección, el total de una página), pasalo.

      for sobre un array y foreach sobre una List<T> cuestan lo mismo: el compilador conoce el enumerador de List<T> (es una struct) y no asigna nada. La misma lista vista como IEnumerable<int> ya cuesta el doble y asigna el enumerador en el heap (40 B), porque pasa por la interfaz. Sum de LINQ está en ese segundo grupo: no es «LINQ es lento», es que la interfaz esconde el tipo concreto.

      LINQ contra el bucle en una consulta real (filtrar por estado y sumar): el bucle tarda 2,5 veces menos, pero mirá la escala: la diferencia son 4 µs por cada mil pedidos. En un endpoint que hace esto una vez, nada. En uno que lo hace por cada fila de una grilla de 10.000 filas, 40 ms. Lo que sí es gratis es elegir bien el operador: MinBy hace una pasada y no asigna casi nada; OrderBy(...).First() ordena los mil para quedarse con uno.

      Any() contra Count > 0: sobre una List<T> las dos son despreciables (Any() tiene atajo para ICollection), así que elegí la que se lea mejor. La regla de verdad es otra: nunca Count() con paréntesis sobre un IEnumerable que no sea una colección, porque lo recorre entero.

      Qué me llevo

      • new List<T>(capacidad) cuando la sabés. Es la optimización más barata que existe.
      • LINQ es 2 o 3× más lento que el bucle equivalente y asigna un poco. Está bien en casi todos lados; pasalo a bucle solo donde el perfilador lo marque.
      • Para «el menor» o «el mayor», MinBy/MaxBy (.NET 6+), no OrderBy().First().
      • Evitá exponer IEnumerable<T> en el camino caliente: la interfaz te cuesta el enumerador en el heap y el despacho virtual.

      Capítulo 5Buscar por clave: la lista no es un índice

      Mil pedidos en una lista, y hay que buscar cien por id. Lo que uno escribe sin pensar es lista.FirstOrDefault(p => p.Id == id) adentro de un bucle.

      [Benchmark(Baseline = true)] public int ListFind100() { ... _lista.Find(p => p.Id == k) ... }
[Benchmark] public int ListFirstOrDefault100() { ... _lista.FirstOrDefault(p => p.Id == k) ... }
[Benchmark] public int Dictionary100() { ... _dic.TryGetValue(k, out _) ... }                 // diccionario armado una vez
[Benchmark] public int ToDictionaryYBuscar100() { var d = _lista.ToDictionary(p => p.Id); ... d.TryGetValue(k, out _) ... }
[Benchmark] public int JoinLinq100() => _claves.Join(_lista, k => k, p => p.Id, (k, p) => p).Count();
      VarianteMedia por operaciónContra la baseMemoria por operación
      ListFind100 base70,2 µs1,00×8,59 KB
      ListFirstOrDefault100349,2 µs5,0× más lento12,5 KB
      Dictionary100331,8 ns200× más rápido0 B
      ToDictionaryYBuscar10013,4 µs5,2× más rápido30,3 KB
      JoinLinq10049,4 µs1,42× más rápido102,3 KB

      Cien búsquedas lineales sobre mil elementos son hasta 100.000 comparaciones: es el clásico O(n·m) que no se nota con datos de prueba y explota en producción. El diccionario ya armado es 200 veces más rápido. Y la parte que más sorprende: armar el diccionario adentro del método, usarlo cien veces y tirarlo, igual es 5× más rápido que buscar con Find, aun pagando 31 KB de memoria. El punto de equilibrio está muy bajo: con más de 10 o 20 búsquedas sobre la misma lista, ya conviene indexarla.

      Dos detalles. List<T>.Find (el método de la lista) es 5× más rápido que FirstOrDefault (el de LINQ) con el mismo predicado, porque recorre el array interno directo en vez de pasar por el enumerador y la interfaz. Y el Join de LINQ hace por adentro exactamente lo que hace ToDictionary (una tabla hash), así que es la forma declarativa de la misma idea; con 100 KB de memoria, eso sí.

      Qué me llevo

      • Un FirstOrDefault adentro de un bucle es un diccionario que falta. ToDictionary o ToLookup antes del bucle, siempre.
      • Sobre una List<T>, Find/FindIndex/Exists le ganan a FirstOrDefault/Any con predicado.
      • Para cruzar dos colecciones, Join o GroupJoin: es legible y ya es O(n+m).

      Capítulo 6Un struct como clave de diccionario

      Una clave compuesta (dos enteros) para un Dictionary. Hay cuatro formas de escribirla y una es una trampa.

      public struct ClaveSinEquatable { public int A; public int B; }          // la trampa
public struct ClaveConEquatable : IEquatable<ClaveConEquatable> { ... Equals(ClaveConEquatable o) ... GetHashCode() => HashCode.Combine(A, B); }
public readonly record struct ClaveRecord(int A, int B);                // el compilador genera todo
// y la tupla (int, int)

[Benchmark(Baseline = true)] public int StructSinEquatable() { ... _sin[new ClaveSinEquatable { A = i, B = i * 2 }] ... }  // 1.000 búsquedas
[Benchmark] public int StructConEquatable() { ... _con[new ClaveConEquatable { A = i, B = i * 2 }] ... }
[Benchmark] public int RecordStruct() { ... _rec[new ClaveRecord(i, i * 2)] ... }
[Benchmark] public int TuplaValor() { ... _tupla[(i, i * 2)] ... }
      VarianteMedia por operaciónContra la baseMemoria por operación
      StructSinEquatable base68,4 µs1,00×70,3 KB
      StructConEquatable24,2 µs2,8× más rápido0 B
      RecordStruct16,6 µs4,1× más rápido0 B
      TuplaValor24,8 µs2,8× más rápido0 B

      Un struct sin Equals ni GetHashCode propios hereda los de ValueType, que usan reflexión para comparar campo por campo y boxean la clave en cada llamada: 72 B de basura por búsqueda y 3 a 4× el tiempo. Implementar IEquatable<T> lo arregla; record struct lo hace solo, y encima le ganó a la implementación a mano porque el compilador genera un GetHashCode con EqualityComparer<int>.Default que el JIT reduce a una suma de enteros. La tupla (int, int) está bien también: implementa IEquatable.

      Qué me llevo

      • Una clave compuesta es un readonly record struct. Una línea, sin trampas, la más rápida.
      • Si tenés un struct a mano como clave o en un HashSet, implementá IEquatable<T> y GetHashCode. El analizador CA1815 lo pide.

      Capítulo 7Boxing, struct contra class, lambdas y params

      Cosas que asignan memoria sin que se vea en el código.

      Boxing es convertir un tipo por valor en un objeto del heap. ArrayList lo hace con cada int (24 B por elemento, 32 KB en total y 6× el tiempo); hoy nadie usa ArrayList, pero el mismo boxing aparece en string.Concat("n=", n), en string.Format con enteros, en object como parámetro, en un struct pasado a una interfaz. Se ve en la columna de memoria, no en el código.

      Mil structs en un array son una sola asignación contigua de 16 KB; mil clases son 1.001 objetos dispersos, 40 KB y 3× el tiempo, y después el GC tiene que visitar cada uno. Para datos chicos e inmutables que viven en colecciones grandes (puntos, rangos, montos con moneda), readonly record struct.

      Una lambda que captura una variable local asigna un objeto de clausura cada vez que se ejecuta el método (96 B acá); una que no captura (static x => ...) se cachea una sola vez y no asigna nunca. La diferencia de tiempo es chica (10 %); la de memoria es de 0 a 96 B por llamada. Y params asigna un array por llamada aunque pases dos valores: 20× más lento que una sobrecarga con parámetros fijos. Por eso el framework tiene string.Concat(a, b), (a, b, c) y recién después params; C# 13 agrega params ReadOnlySpan<T> que no asigna.

      Qué me llevo

      • Mirá la columna de memoria: donde dice más de 0 B en algo que no debería asignar, hay boxing o una clausura.
      • Lambdas static en el camino caliente; si captura algo, que capture poco y sepas que asigna.
      • Sobrecargas con 1, 2 y 3 parámetros antes del params, en las APIs que se llaman mucho.

      Capítulo 8Excepciones: cuánto cuesta un throw

      Un throw con su catch cuesta entre 6 y 8 µs: unas mil veces más que el if que lo evita. En el camino normal (10 % de entradas inválidas) usar Parse con catch en vez de TryParse es 135× más lento, y con todas inválidas más de 1.000×. La memoria de la tabla es la del objeto excepción y su stack trace: 224 B en el caso simple, 500 B por entrada inválida en el parseo.       ¿Importa? Una excepción cada tanto, no: 7 µs en un pedido de 20 ms es nada. Importa cuando se vuelve control de flujo: validar con Parse, buscar con First y atrapar InvalidOperationException, abrir archivos a ver si existen, un catch por fila en una importación. Ahí la API que procesaba 10.000 filas por segundo pasa a procesar 1.000, y el perfilador muestra la CPU en RaiseException y en armar stack traces. El contador exception-count de dotnet-counters es la forma de verlo en producción: si es de cientos por segundo en régimen normal, hay un catch trabajando de if.

      Qué me llevo

      • TryParse, TryGetValue, FirstOrDefault, File.Exists: para todo lo que puede fallar «normalmente», la variante que devuelve bool o null.
      • Las excepciones son para lo excepcional, y ahí da igual lo que cuesten. .NET 9 las hizo 2 a 4× más baratas; sigue siendo mil veces un if.
      • Mirá exception-count en producción. Cero en régimen es el objetivo.

      Capítulo 10Regex: interpretada, compilada, generada, o ninguna

      Validar cien direcciones de correo (un cuarto inválidas) con la misma expresión regular construida de cinco maneras, y a mano sin regex.

La variante estática Regex.IsMatch(texto, patrón) zafa porque el runtime cachea los últimos 15 patrones, pero depende de que no haya más de 15 distintos en toda la aplicación.

      La segunda: RegexOptions.Compiled rinde 2,4× sobre la interpretada y el source generator ([GeneratedRegex]) 2,7×, con la ventaja de que el código generado se ve, se depura y no cuesta nada al arrancar (la compilada genera IL en tiempo de ejecución, y eso en una API son decenas de ms por regex en el primer uso). No es un argumento contra las regex (la versión a mano valida menos cosas), es para recordar que una regex es un intérprete de un lenguaje, y que si lo que querés saber es «¿tiene una arroba y un punto después?», no hace falta uno.

      Qué me llevo

      • Nunca new Regex(...) adentro de un método que se llama más de una vez. static readonly o [GeneratedRegex].
      • Patrón constante: [GeneratedRegex]. Patrón que viene de configuración: RegexOptions.Compiled si se usa mucho, y siempre con matchTimeout si viene del usuario.
      • Para «empieza con», «contiene», «termina con» y «es un número», los métodos de string son más claros y 20× más rápidos.

      • El source generator vale la pena en DTOs que se serializan mucho, en AOT y en el arranque; no cambia la deserialización.

      Cien lecturas de un diccionario en memoria, escritas de todas las formas en que se ven en un repositorio real: sincrónica, devolviendo Task.FromResult, con un método async que nunca espera, con ValueTask, con Task.Yield, con Task.Run, y la peor: con .Result.

      private int Sync(int k) => _cache[k];

      Un método async cuyo resultado ya está disponible (el caché que casi siempre acierta, el valor que a veces hay que ir a buscar) cuesta unos 20 ns y 70 B por llamada: el objeto Task<int>. Si además hace await sobre otra Task ya completada, casi se duplica. No es mucho, pero es un objeto por llamada en el heap, y en un método que se llama un millón de veces por segundo son 70 MB/s de basura. Para eso existe ValueTask<T>: cuando el resultado está, no asigna nada; cuando no está, se comporta como una Task. Es la elección correcta para «casi siempre sincrónico» y la equivocada para «casi siempre asincrónico» (ahí asigna igual y encima tiene reglas de uso más estrictas: se espera una sola vez).

      La escala cambia cuando el código salta de hilo: Task.Yield o Task.Run para algo trivial cuestan 300 a 400 ns por operación, porque cada uno encola un work item en el thread pool y espera que otro hilo lo tome. Y .Result sobre un Task.Run es 4× peor que esperarlo con await, aun en un benchmark que no sufre inanición: el hilo que llama se duerme y se despierta por cada uno. En una API, además, es el camino directo a la inanición del thread pool (hay un simulador de eso en El thread pool en vivo).

      Qué me llevo

      • No hagas async lo que no espera nada: devolvé el valor, o Task.FromResult, o mejor ValueTask si la firma tiene que ser asincrónica.
      • ValueTask<T> para métodos que casi siempre completan sincrónicamente (cachés, buffers). Task<T> para todo lo demás.
      • Task.Run es para trabajo de CPU largo, no para «hacerlo asincrónico». Y nunca con .Result atrás.

      Un LogDebug que no va a salir igual cuesta si lo escribís con interpolación: la cadena se arma antes de llamar al método (94 ns y 96 B para nada). Con la plantilla y los argumentos tampoco es gratis: los tres valores se boxean en un object[] (128 B) antes de que el logger decida que no le interesa. Las tres formas que no cuestan nada cuando el nivel está apagado son IsEnabled antes, LoggerMessage.Define y el source generator [LoggerMessage]: 2 a 3 ns, 0 B. Un servicio con cientos de LogDebug y LogTrace por pedido paga esto en cada pedido, en producción, para no escribir nada.

      Cuando el mensaje sí sale, la plantilla estructurada es la más cara de las tres (241 ns, 224 B): además de formatear el texto arma el objeto con los pares nombre/valor, que es justamente lo que un sink estructurado (Seq, Elastic, OpenTelemetry) necesita. La interpolada parece más barata, pero pierde la estructura: en el sink queda texto y chau. El source generator da las dos cosas: estructura y 96 B. Ojo que acá el proveedor descarta todo; con un sink real (consola, archivo, red) el costo del mensaje que sale lo domina el sink, no el formateo.

      Qué me llevo

      • Nunca interpolación en un log: pierde la estructura y se paga aunque esté apagado. El analizador CA2254 lo marca.
      • Para los logs frecuentes (por pedido, por fila): [LoggerMessage]. Para el resto, la plantilla está bien.
      • Un IsEnabled antes de armar algo caro para loguear (un JSON, un ToString grande) es la forma de no pagarlo.

      Pedir la hora cuesta unos 30 ns, y DateTime.Now apenas más que UtcNow (en Linux el runtime cachea la zona horaria; en Windows antes era peor). O sea: no hace falta cachear UtcNow «por rendimiento», aunque sí conviene inyectar un TimeProvider por testeabilidad. Para medir intervalos, Stopwatch.GetTimestamp() y Stopwatch.GetElapsedTime(inicio) (.NET 7+) es lo correcto, no restar dos DateTime.

      Formatear con "O" (ISO 8601 redondo) es casi 3× más rápido que un formato a medida porque tiene un camino especial; y TryFormat sobre un buffer no asigna. DateTime.Parse sin formato le ganó por poco a ParseExact acá, pero ParseExact es el que no te va a sorprender con una cultura distinta en el servidor. Guid.NewGuid() cuesta 360 ns porque pide bytes aleatorios al sistema operativo; .NET 9 agrega Guid.CreateVersion7(), que es ordenable por tiempo y el que querés como clave de base (hay un experimento sobre eso: GUID o identity).

      Qué me llevo

      • El reloj es barato. Medí intervalos con Stopwatch, no con DateTime.
      • Para fechas en JSON y logs, "O": es el formato más rápido y el único que no se malinterpreta.
      • Un GUID son 360 ns: nada en un pedido, 36 ms si generás 100.000 en un bucle.

      Para terminarLa chuleta: qué vale la pena y qué no

      Lo que de verdad se nota, ordenado por cuánto se nota. Lo de arriba son errores que convierten microsegundos en milisegundos; lo de abajo son nanosegundos que solo importan en un bucle caliente.

      Esto sí (órdenes de magnitud)

      • Excepciones como control de flujo: 1.000× el if. TryParse, TryGetValue, FirstOrDefault.
      • FirstOrDefault adentro de un bucle sobre una lista: 200× un diccionario. ToDictionary antes del bucle.
      • new Regex(...) por llamada: 22× y 6 KB de basura. static readonly o [GeneratedRegex].
      • StartsWith/EndsWith sin StringComparison: 10× por pasar por la cultura. Ordinal.
      • params, boxing y clausuras en APIs que se llaman millones de veces: asignan sin que se vea.
      • Logs con interpolación o LogDebug sin IsEnabled: ~100 ns y ~100 B por cada log apagado. [LoggerMessage].
      • Newtonsoft donde podría ser System.Text.Json: 2× el tiempo y 4× la memoria en cada respuesta de la API.
      • Reflexión sin cachear (GetProperty + GetValue): 12× y boxing. Delegados compilados, o source generators.
      • .Result y Task.Run para esperar: 4× un await, y en una API el camino a la inanición.

      Esto, solo en el camino caliente

      • LINQ vs. bucle: 2 a 3×, unos µs por cada mil elementos. MinBy en vez de OrderBy().First().
      • Split/Substring vs. Span: 2 a 12× y 0 B. En parsers.
      • string.Join/interpolación vs. +=/string.Format: 2 a 3× y la mitad de memoria.
      • ValueTask en métodos que casi siempre completan sincrónicamente: 0 B contra 70 B por llamada.
      • struct como clave de diccionario: record struct, 4× y sin boxing.
      • Capacidad inicial de las listas: casi 2× y la mitad de memoria.
      • Enum.ToString(): 24 B por llamada; un switch no asigna.
      • Interlocked vs. lock para un contador: 4×.

      Esto no importa (dejá de discutirlo)

      • Virtual, interfaz o delegado contra llamada directa: una fracción de nanosegundo. sealed es prolijo, no rápido.
      • Any() contra Count > 0 sobre una lista. for contra foreach sobre una List<T>.
      • DateTime.Now contra UtcNow. Pedir la hora son 30 ns.
      • HasFlag, Enum.Parse, IsDefined: ya no asignan ni son lentos.
      • El 95 % del código, que corre una vez por pedido y no en un bucle. Ahí lo único que importa es que se entienda.
      La regla. Antes de optimizar, medí: dotnet-counters para el GC y las excepciones, dotnet-trace o el perfilador de Visual Studio para la CPU, y BenchmarkDotNet para comparar dos formas de hacer lo mismo. Cambiá lo que el perfil marque, con el número antes y después en el PR. Lo demás es superstición, aunque venga con tabla.

      ApéndiceCómo reproducirlo y fuentes

      El proyecto completo está en benchmarks/: un .csproj de .NET 8 con BenchmarkDotNet, Newtonsoft.Json y Microsoft.Extensions.Logging, y un archivo por capítulo con el código tal cual se midió. Para correrlo todo (tarda unos 45 minutos con la configuración corta):

      cd escritos/cuanto-cuesta-dotnet/benchmarks
dotnet run -c Release -- --filter '*'              # todo
dotnet run -c Release -- --filter '*Cadenas*'      # un capítulo
dotnet run -c Release -- --list flat               # ver los 129

      Los resultados quedan en BenchmarkDotNet.Artifacts/results/; exportar.py los convierte en resultados.json y node tablas.js regenera las tablas de esta página. La configuración es ShortRun (3 calentamientos, 5 iteraciones) con MemoryDiagnoser: alcanza para las relaciones entre variantes; si querés el nanosegundo exacto para tu máquina, sacá el ShortRun y dejá el job por defecto (tarda horas).

      Dos advertencias de BenchmarkDotNet que se aplicaron acá: cada benchmark devuelve lo que calcula (si no, el JIT puede eliminar el trabajo), y los datos se arman en el constructor, no adentro del método medido. Lo que se mide es exactamente lo que está en el bloque de código de cada capítulo.
