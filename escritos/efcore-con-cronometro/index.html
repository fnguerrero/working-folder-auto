    EF Core con el cronómetro en la mano

    Trece experimentos sobre lo que Entity Framework Core manda al servidor y lo que trae de vuelta, medidos contra un SQL Server de verdad: viajes, lecturas, filas, bytes y memoria. Para gente que escribe LINQ todos los días y quiere saber qué pasa debajo.

    EF Core 8 · Microsoft.Data.SqlClient · SQL Server 2022 (Developer, Linux) · base «Tienda»: 400.000 pedidos, 1,2 millones de ítems, 1,6 millones de eventos, 50.000 clientes · todos los números y todo el SQL salen de resultados.json, generado por el proyecto experimentos/. Es el hermano de Índices con el cronómetro en la mano: aquel mira el servidor, este mira lo que EF le pide.

    Índice

      Antes de empezarQué se mide y por qué

      Entity Framework Core es muy bueno escondiendo lo que hace. Eso es lo que lo hace cómodo y también lo que hace que una línea de LINQ inocente termine en doscientos viajes al servidor o en 50 MB de filas que nadie va a mirar. Este escrito agarra las situaciones de todos los días (cargar relaciones, paginar, buscar por una lista de ids, insertar de a muchos, preguntar «¿hay alguno?») y las mide, con el SQL que EF realmente mandó al lado.

      Cada variante se corrió seis veces con un contexto nuevo cada vez: la primera, que paga la compilación de la consulta y el JIT, no se cuenta; de las otras cinco se toma la mediana. En cada corrida se mide:

      • Tiempo: lo que tardó la operación completa, del lado de .NET, con el servidor en la misma máquina (un viaje de ida y vuelta cuesta alrededor de medio milisegundo acá; en una red real, varias veces más, y todo lo que dependa de la cantidad de viajes empeora en proporción).
      • Viajes: cuántas veces fue y vino del servidor (ServerRoundtrips de las estadísticas de SqlConnection).
      • Lecturas: páginas de 8 KB que leyó SQL Server para contestar (logical_reads de sys.dm_exec_sessions), que es la medida estable del costo del lado del servidor, como se explica en el escrito de índices.
      • Filas que el servidor devolvió y bytes recibidos por el cliente: lo que viajó por la red.
      • Memoria .NET: bytes asignados en el proceso durante la operación (GC.GetTotalAllocatedBytes), que es lo que después tiene que barrer el recolector.

      La columna «contra la base» compara el tiempo con el de la primera fila de cada tabla, que es siempre la forma más común o más inocente de escribirlo.

      Capítulo 1El N+1: un viaje por cada pedido

      El cliente 2 tiene 200 pedidos con 595 ítems en total. Queremos, para cada pedido, cuántos ítems tiene. Cinco maneras de pedirlo:

      // 1. Cargar los pedidos y después, para cada uno, su colección
var pedidos = ctx.Pedidos.Where(p => p.ClienteId == 2).ToList();
foreach (var p in pedidos) { ctx.Entry(p).Collection(x => x.Items).Load(); n += p.Items.Count; }

// 2. Lo mismo sin darse cuenta: con UseLazyLoadingProxies(), tocar p.Items dispara la carga
foreach (var p in pedidos) n += p.Items.Count;

// 3. Include
ctx.Pedidos.Where(p => p.ClienteId == 2).Include(p => p.Items).ToList();

// 4. Proyectar solo lo que hace falta
ctx.Pedidos.Where(p => p.ClienteId == 2).Select(p => new { p.PedidoId, Cantidad = p.Items.Count }).ToList();

// 5. Proyectar con los ítems adentro
ctx.Pedidos.Where(p => p.ClienteId == 2)
   .Select(p => new { p.PedidoId, Items = p.Items.Select(i => new { i.ProductoId, i.Cantidad }).ToList() }).ToList();

      Include lo resuelve en un viaje, pero mirá la columna de bytes: 329 KB para 200 pedidos, cuando la proyección con los ítems adentro trae lo mismo en 11 KB. Es que Include genera un JOIN y cada fila del resultado repite todas las columnas del pedido, Notas incluida, una vez por ítem:

      SELECT [p].[PedidoId], [p].[ClienteId], [p].[Estado], [p].[Fecha], [p].[Notas], [p].[Total], [i].[ItemId], [i].[Cantidad], [i].[PedidoId], [i].[Precio], [i].[ProductoId]
FROM [Pedidos] AS [p]
LEFT JOIN [Items] AS [i] ON [p].[PedidoId] = [i].[PedidoId]
WHERE [p].[ClienteId] = 2
ORDER BY [p].[PedidoId]

      Y si lo único que hacía falta era el conteo, la proyección con p.Items.Count lo calcula en el servidor y vuelve con 200 filas de dos columnas: 2 KB, 670 lecturas y 3 ms. Diez veces menos que el Include y setenta veces menos que el bucle.

      SELECT [p].[PedidoId], (
    SELECT COUNT(*)
    FROM [Items] AS [i]
    WHERE [p].[PedidoId] = [i].[PedidoId]) AS [Cantidad]
FROM [Pedidos] AS [p]
WHERE [p].[ClienteId] = 2

      Qué me llevo

      • Un foreach que adentro toca una navegación es un N+1, se vea la consulta o no. Con lazy loading no se ve.
      • Include arregla los viajes, no los bytes: repite el padre por cada hijo. Para listados grandes, proyectar.
      • Si lo que querés es un número por pedido, pedí el número: p.Items.Count adentro del Select va al servidor.

      Con un solo Include vienen 3.011 filas (los ítems). Con dos, 12.413: para cada pedido, el servidor arma el producto cartesiano de sus ítems por sus eventos, y cada una de esas filas lleva otra vez las columnas del pedido. Son 7 MB por la red y 24 MB de objetos en .NET, para que EF después descarte los duplicados. Es lo que la documentación llama cartesian explosion, y crece multiplicando: con un tercer Include de colección serían decenas de miles de filas.

      SELECT [t].[PedidoId], [t].[ClienteId], [t].[Estado], [t].[Fecha], [t].[Notas], [t].[Total], [i].[ItemId], [i].[Cantidad], [i].[PedidoId], [i].[Precio], [i].[ProductoId], [e].[EventoId], [e].[Fecha], [e].[PedidoId], [e].[Tipo]

      AsSplitQuery() lo parte en tres consultas (pedidos, ítems, eventos), cada una con solo sus filas: 8.108 en total, 722 KB. Cuesta dos viajes más y pierde la consistencia de una sola lectura (si alguien inserta un evento entre la segunda y la tercera consulta, lo ves), pero para dos o más colecciones es la opción sana. Se puede dejar como comportamiento por defecto con UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery) al configurar el proveedor.

      La proyección es interesante por lo que no arregla: EF Core 8 también la genera como una sola consulta con el mismo producto cartesiano (12.413 filas). Lo que la salva es que las filas son angostas, porque no viaja Notas ni nada que no se haya pedido: 602 KB en vez de 7 MB. Si a la proyección le agregás AsSplitQuery(), también se parte.

      Qué me llevo

      • Un Include de colección está bien. Dos o más sobre la misma entidad, con AsSplitQuery() o proyectando.
      • Mirá las filas que vuelven, no solo los viajes: 1.000 pedidos no deberían ser 12.000 filas.

      Capítulo 3Lo que cuesta que EF te siga el rastro

      Por defecto, cada entidad que devuelve una consulta queda registrada en el change tracker del contexto, con una copia de sus valores originales, para poder detectar qué cambió en el SaveChanges. Es lo que hace que modificar una propiedad y guardar «simplemente funcione», y se paga en memoria y en tiempo. Leemos 20.000 pedidos:

q.ToList();                                                     // rastreando
q.AsNoTracking().ToList();
q.Include(p => p.Cliente).ToList();                             // rastreando (los 20.000 son del cliente 1)
q.Include(p => p.Cliente).AsNoTracking().ToList();
q.Include(p => p.Cliente).AsNoTrackingWithIdentityResolution().ToList();
var l = q.ToList(); ctx.SaveChanges();                          // sin haber cambiado nada

      Las lecturas y los bytes son iguales en todas: el servidor hace lo mismo. La diferencia es toda del lado de .NET. Rastrear 20.000 pedidos cuesta entre dos y cuatro veces el tiempo y 22 MB más que no rastrearlos (186 ms contra 49 en esta corrida; en otra dio 131 contra 54: el rastreo es trabajo de CPU en .NET y baila más que lo que hace el servidor). Para una pantalla que lista y no modifica, ese trabajo es puro desperdicio; AsNoTracking() en la consulta, o ChangeTracker.QueryTrackingBehavior = NoTracking en el contexto de lectura, lo evita.

      Lo del Include(p => p.Cliente) rastreando es otra cosa, y es la sorpresa del capítulo: 1,9 segundos en vez de 190 ms, sin que el servidor haya hecho nada distinto. El culpable es la colección de navegación del otro lado: cuando EF materializa cada pedido tiene que agregarlo a Cliente.Pedidos, y esa colección estaba inicializada en la entidad como new List<Pedido>(). Para no duplicar, EF pregunta Contains antes de agregar, y Contains en una lista es recorrerla: con 20.000 pedidos del mismo cliente son 200 millones de comparaciones. Con new HashSet<Pedido>() la misma consulta vuelve a su tiempo normal: 169 ms, once veces menos. EF crea HashSet cuando la colección está en null; el problema aparece cuando uno «ayuda» inicializándola con una lista. AsNoTrackingWithIdentityResolution() tiene exactamente el mismo problema (es la misma fijación de navegaciones, sin el rastreo), y con HashSet se arregla igual (2,8 segundos contra 191 ms).

      AsNoTracking() a secas con el Include es rápido por el camino opuesto: no hace la fijación, así que materializa 20.000 instancias distintas del mismo cliente (una por pedido, 12 MB más de memoria). Si lo que hacés es mostrar el nombre del cliente al lado de cada pedido, da lo mismo; si vas a comparar referencias o armar un grafo, no.

      La última fila es un SaveChanges() sin ningún cambio sobre 20.000 entidades rastreadas: DetectChanges tiene que comparar cada propiedad de cada entidad con su copia original. Acá son unos 20 ms y 17 MB más, poca cosa; en el capítulo 8 vamos a ver lo que pasa cuando eso se hace 2.000 veces.

      Qué me llevo

      • Consulta que no va a modificar nada: AsNoTracking(). Mitad de tiempo, un tercio menos de memoria.
      • No inicialices las colecciones de navegación con List. Dejalas en null o usá HashSet: las fijaciones son O(1) en vez de O(n).
      • AsNoTracking() con Include de referencia duplica el padre por cada hijo. Si eso importa, AsNoTrackingWithIdentityResolution().

      • Para listar, proyectá a un record o a un tipo anónimo con las columnas que la pantalla usa. La entidad completa es para cuando la vas a modificar.
      • Todo lo que esté después de un ToList(), AsEnumerable() o ToArray() se ejecuta en .NET sobre lo que ya viajó. Los agregados, filtros y ordenamientos van antes.

      Capítulo 5Paginar con Skip o con la última clave

      La forma natural de paginar en LINQ es Skip(n).Take(50), que EF traduce a OFFSET … FETCH. El servidor, para saltear 399.950 filas, tiene que leerlas y descartarlas. La alternativa es keyset o paginación por cursor: recordar la clave de la última fila mostrada y pedir las siguientes:

      // OFFSET: la página 8.000 de 50
ctx.Pedidos.OrderBy(p => p.PedidoId).Skip(7999 * 50).Take(50).ToList();

// Keyset: «las 50 siguientes a la última que mostré»
ctx.Pedidos.Where(p => p.PedidoId > ultimo).OrderBy(p => p.PedidoId).Take(50).ToList();

// Lo mismo ordenando por fecha (hay índice sobre Fecha) y desempatando por id
ctx.Pedidos.OrderBy(p => p.Fecha).ThenBy(p => p.PedidoId).Skip(7999 * 50).Take(50).ToList();
ctx.Pedidos.Where(p => p.Fecha > f || (p.Fecha == f && p.PedidoId > id))
   .OrderBy(p => p.Fecha).ThenBy(p => p.PedidoId).Take(50).ToList();

      Las dos primeras filas mandan exactamente el mismo texto SQL, WHERE [c].[Email] = @__email_0. La diferencia está en algo que no se ve en el SQL: el tipo del parámetro. Si el modelo dice .IsUnicode(false) (o HasColumnType("varchar(200)")), EF declara @__email_0 varchar(200) y el servidor hace un seek: 3 lecturas. Si no lo dice, los string de .NET son nvarchar(4000), comparar varchar con nvarchar obliga al servidor a convertir cada valor de la columna al tipo del parámetro, y el índice se recorre entero: 257 lecturas, que es el índice completo de 50.000 clientes. Con 5 millones serían 25.000 lecturas por cada login. Es el bug de rendimiento más silencioso que hay en un proyecto EF con una base que viene de antes, porque funciona, devuelve lo correcto y no avisa.

      Las demás son las reglas de sargabilidad de siempre, vistas desde LINQ: StartsWith se traduce a LIKE 'x%' y usa el índice (3 lecturas); Contains y EndsWith son LIKE '%x%' y LIKE '%x' y lo recorren (257); ToLower() y Trim() envuelven la columna en una función y lo mismo. Si la comparación tiene que ser sin distinguir mayúsculas, la respuesta no es ToLower() sino la intercalación de la columna (en SQL Server por defecto ya es case insensitive); si hay que buscar adentro del texto, es un índice de texto completo o un campo normalizado, no un Contains.

      Qué me llevo

      • Toda columna varchar de la base tiene que estar como IsUnicode(false) en el modelo (o en el HasColumnType). Si no, cada búsqueda por esa columna es un scan.
      • StartsWith usa el índice; Contains, EndsWith, ToLower(), Trim() y cualquier función sobre la columna, no.

      Capítulo 12Parámetros, constantes y la caché de planes

      SQL Server guarda un plan de ejecución por cada texto SQL distinto. Si el valor que cambia entre consultas viaja como parámetro, hay un texto y un plan; si va pegado en el SQL, hay un texto y un plan por valor. Corremos 300 veces la misma consulta con 300 valores distintos, vaciando la caché antes de cada variante y contando los planes al final:

      ctx.Pedidos.FromSqlRaw($"SELECT TOP 10 * FROM dbo.Pedidos WHERE ClienteId = 1 AND Total > {total}").Count();   // ¡no!
ctx.Pedidos.FromSql($"SELECT TOP 10 * FROM dbo.Pedidos WHERE ClienteId = 1 AND Total > {total}").Count();      // interpolado: parámetro
ctx.Pedidos.Where(p => p.ClienteId == 1 && p.Total > total).Take(10).Count();                                 // variable capturada
// Y un árbol de expresión armado a mano con Expression.Constant(total), como hacen algunos «filtros dinámicos»

      FromSqlRaw con el valor interpolado en el string deja 300 planes en caché y tarda siete veces más (640 ms contra 92): cada consulta se compila de cero, y las lecturas suben de 1.262 a 12.923 porque compilar también lee (estadísticas, metadatos). Y es, además, una inyección de SQL esperando que total venga de un usuario. FromSql con la misma cadena interpolada parece lo mismo y es lo contrario: toma los valores de la interpolación y los manda como parámetros. La diferencia entre las dos es una letra en el nombre del método.

      LINQ con una variable capturada hace lo correcto solo: total sale como @__total_0, y Take(10) también va parametrizado. La última fila es el mismo LINQ pero con el valor metido como Expression.Constant en un árbol armado a mano: EF lo trata como constante y lo pega en el SQL ([p].[Total] > 1017.0), con lo cual vuelven los 300 planes, y además EF tampoco encuentra la consulta en su propia caché (el árbol es distinto cada vez) y la compila de nuevo: 744 ms. Si armás filtros dinámicos con la API de expresiones, el valor va en una variable capturada o en EF.Parameter(…), no en un Constant.

      Qué me llevo

      • FromSql (o FromSqlInterpolated), nunca FromSqlRaw con un string armado.
      • En LINQ, los valores en variables son parámetros; los literales y los Expression.Constant van pegados en el SQL.
      • Si querés saber si tu aplicación hace esto hoy: SELECT COUNT(*) FROM sys.dm_exec_cached_plans WHERE objtype = 'Adhoc', y que no sean miles.

      Para un pedido, async cuesta 0,3 ms más y no importa. Para 20.000 pedidos cuesta 2,6 veces más (117 ms contra 46) y 15 MB más de memoria. Y para los documentos grandes es un desastre: 892 ms contra 140, y 944 MB asignados contra 117, para traer 39 MB. Es un problema conocido de Microsoft.Data.SqlClient (dotnet/SqlClient#593): cuando un valor no entra en un paquete de red, el lector asincrónico vuelve a procesar lo que ya tenía del valor con cada paquete nuevo, así que leer una columna de N paquetes cuesta N² en vez de N, y cada pasada asigna. Con textos de 8 KB apenas se nota; con 80 KB, 7 veces; con 1 MB, no termina.

      Esto no quiere decir «no usés async». Async es lo que hace que una API no se quede sin hilos mientras espera a la base (está medido en El thread pool en vivo). Quiere decir dos cosas más precisas: no traigas columnas grandes que no necesitás (la tercera fila: solo el título, 2 ms), y si tenés que traer un blob grande, traelo aparte, en una consulta propia, con CommandBehavior.SequentialAccess y un stream, o sincrónica en un Task.Run si no queda otra.

      Qué me llevo

      • Async en EF tiene un costo fijo chico por consulta y uno grande por cada columna gorda.
      • Las columnas nvarchar(max) y varbinary(max) se proyectan afuera salvo cuando se necesitan, y entonces se leen solas.

      ConclusiónLo que EF no te va a decir

      Trece capítulos y en ninguno el problema fue que EF Core traduzca mal. Tradujo bien el N+1, bien la explosión cartesiana, bien el ToList().Any(), bien el Contains sin índice, bien el Local.FirstOrDefault. Hizo lo que se le pidió, con un SQL razonable, en el momento en que se le pidió. El costo estaba en qué se pidió (la entidad entera, todas las filas, un viaje por elemento), en cuándo (antes o después del ToList()), en cómo estaba el modelo (List en vez de HashSet, un string sin IsUnicode(false)) y en lo que había del otro lado (un índice que faltaba).

      La herramienta para ver todo esto sin un escrito como este es la misma que se usó acá: mirar el SQL que sale (LogTo en desarrollo, o un interceptor que cuente comandos por request y grite cuando pasan de diez) y mirar lo que vuelve (filas y bytes). Viajes, lecturas, filas, bytes: si uno de los cuatro es raro, la consulta está mal escrita, y si los cuatro son normales y sigue lenta, el problema no es de EF.
